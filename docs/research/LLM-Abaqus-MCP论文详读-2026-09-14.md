# LLM 驱动 Abaqus MCP 自动化论文详读（2026）

> 论文：Eun Hyun Kim, Jae Hyuk Lim, **Development of an LLM-Driven Abaqus MCP-Integrated Finite Element Analysis Automation System with Hallucination Suppression and Performance Improvement**, *Journal of the Computational Structural Engineering Institute of Korea*, 39(2), 123–135, 2026. DOI: 10.7734/COSEIK.2026.39.2.123。
>
> 本记录基于全文 13 页及主要图表（尤其 Tables 5–9）的阅读。这里记录论文声称、可直接观察到的实验结果，以及与本项目的工程含义；没有复现作者系统，也没有把论文结果当成本项目能力证明。

## 1. 这篇论文实际解决什么问题

论文实现了一套由 LLM 驱动、通过 MCP 调用 Abaqus 的有限元自动化系统，目标不只是“让模型生成 Abaqus 脚本”，而是处理三个更具体的问题：

1. **需求缺失导致的建模漂移**：相同但不完整的自然语言请求，多次执行会得到不同的几何、载荷、网格等定义。
2. **运行错误后的自动修复**：把 Abaqus 的错误日志重新反馈给 Agent，使其修改脚本后再次执行。
3. **后续相似任务的经验复用**：把成功脚本和修复经验记录到长期文本中，后续任务再读取。

论文采用 Claude Code + Claude Opus 4.6，主 Agent 配合一个子 Agent；Abaqus 侧通过基于 FastMCP 的 stdio MCP 服务暴露工具，运行环境为 Windows、Abaqus 2025、Python 3.10。

这里最值得关注的并不是 MCP 本身。MCP 主要承担工具接入和协议边界；论文真正试图改善可靠性的机制，是**结构化需求确认、错误反馈闭环和经验复用**。

## 2. 系统结构与工作流

论文给出的流程可以概括为七步（Fig. 3，论文印刷页 127）：

1. User Query
2. Requirements Structuring
3. Script Generation
4. Script Submission / Abaqus Check
5. Abaqus Run / Self-Correction
6. Result Extraction
7. Final Report + `LESSONS_LEARNED.md`

MCP 一共暴露 11 类工具（Table 1，印刷页 126），包括 Abaqus GUI/进程状态、运行脚本、提交 INP、获取进程状态、列文件、读取输出文件、提取 ODB 数据、打开 Viewer、保存报告等。它们的共同特点是把外部 CAE 系统的**执行、状态、日志和结果提取**暴露成显式工具调用。

从本项目视角，这种工具边界与我们当前三个 typed runtime tools 的方向一致：模型不应该凭空假定外部运行状态，而应通过受控工具得到执行事实。不过论文没有给出像本项目这样严格的运行预算、路径归属、artifact freshness、独立 verifier 等宿主约束。

## 3. 三个核心机制

### 3.1 结构化需求与执行前确认

论文用 `SPEC TEMPLATE.md` 把自然语言需求整理成 `Spec.JSON`，并给字段标记来源（论文印刷页 131，Table 7）：

- `user`：用户明确给出的值；
- `llm_assumed`：LLM 补出的假设；
- `user_confirmed`：用户确认后的值。

随后只有经过用户确认，才进入 Abaqus 执行。

这个机制的价值在于把“模型脑内补全”变成显式对象，让缺失项和假设对用户可见，并给执行设置门槛。论文的实验也显示，如果请求保持含糊，相同 prompt 重复执行会出现明显的几何、载荷和网格差异；固定确认后的 spec 再重复执行，结果则稳定得多。

对本项目来说，**可迁移的是结构化缺口暴露和执行阻断**，而不是允许模型先给物理参数填常见值。当前项目规定：如果缺少会改变物理模型的必需输入，应在任何 Abaqus 调用前澄清。这比论文里的 `llm_assumed -> user_confirmed` 更严格，也更适合我们现在的 Gold/evaluator 合同。

### 3.2 错误驱动的自修复

论文把 Abaqus `.dat/.log` 等错误反馈给主 Agent；主 Agent 写 `ERROR_CONTEXT.md`，子 Agent结合它和 `FIX_HISTORY.md` 修改脚本，再循环执行（印刷页 127）。

这个模式说明一个很实用的工程事实：CAE Agent 不能只拿最终 exit code，它需要**原始运行证据和高信号错误上下文**，否则很难形成可靠的修复循环。

但论文把诊断状态主要放在可变 Markdown 文件和多 Agent 协作中。对本项目而言，更合适的对应物已经是宿主持有的 execution journal、原始 stdout/stderr、solver 日志摘录、API 错误提示和独立 verifier。论文可以作为“错误证据应回流给模型”的外部佐证，但不足以说明我们应切换为多 Agent，或把诊断历史做成自由文本记忆。

### 3.3 `LESSONS_LEARNED.md` 与经验复用

系统在成功任务后把脚本经验和修复策略写入 `LESSONS_LEARNED.md`，后续任务读取。作者在风力机连续案例中把后期运行次数下降、耗时缩短与经验积累联系起来。

这个想法和我们最近讨论的 Skill、领域包、RAG 长尾证据很接近：**把一次任务的可复用知识转化成未来任务可读取的上下文**。

但论文并没有建立“哪些经验可泛化、何时应该加载、何时失效”的严格机制，也没有证明自由累积的经验文件在广泛任务上稳定有效。后面的风力机 Case 2–4 本身就是在前一个已验证模型上连续修改，因此代码复用和任务相似度是很强的混杂因素。对本项目，这更支持“成功经验应经过筛选和验证后进入 Skill/Catalog/RAG”，而不是自动把所有修复历史晋升为长期知识。

## 4. 实验结果应该怎样解读

### 4.1 基础自动化：4/4 能跑完，但运行成功不等于建模正确

Section 3.1 一共测试 4 个案例（Table 5，印刷页 129）：悬臂梁静力、中心孔板静力、L 形支架静力、阶梯轴模态。四个案例都完成了端到端执行，自修复最多 2 次，平均约 0.5 次，耗时约 3 分 59 秒到 10 分 2 秒。

论文自己明确指出，**执行成功并不保证符合用户原始意图**：中心孔板的载荷理解一度错误，L 形支架还遗漏了螺栓孔。这一点对本项目非常重要，因为它直接支持我们现在把 execution evidence 与 task-specific physics/intent verification 分开的设计。

悬臂梁案例也很有代表性。作者的 C3D8R 模型最大位移为 7.571 mm，与 Timoshenko 梁理论值 7.634 mm 相差约 -0.82%；但最大应力为 291.25 MPa，而理论值为 600 MPa，相差约 -51.5%。作者将主要原因归结为固定端附近的粗网格和减缩积分。这个结果说明：**某个标量吻合、Solver 成功、甚至报告生成完成，都不能替代模型质量和物理结果审查。**

### 4.2 不做需求确认：相同含糊 prompt 会产生明显变异

Section 3.2.1 把同一个含糊的悬臂梁 prompt 重复 4 次（Table 6，印刷页 130）。四次都能完成，最多 1 次错误修复，耗时约 1 分 32 秒到 3 分 40 秒；但几何、载荷、网格等建模参数在不同运行之间发生了明显变化。

这项实验真正证明的是：**当任务定义本身没有冻结时，Agent 的“成功执行”可以对应不同的问题定义。** 因此，仅用成功率评测这类系统，会掩盖规格漂移。

### 4.3 结构化确认后：一个简单案例上得到 5/5 一致结果

Section 3.2.2 先整理缺失项，让用户确认固定 spec，再重复 5 次。五次均成功、零错误修复，轮廓图和结果保持一致，耗时约 1 分 58 秒到 2 分 22 秒（印刷页 131）。

这为“先冻结明确规格再执行”提供了很直观的证据。但实验只有一个简单悬臂梁，且模板、确认流程、固定输入和可能的 prompt 变化同时存在，无法单独估计每一项机制的因果贡献。更稳妥的表述是：**明确且固定的 problem spec 显著改善了这个测试中的可重复性。**

### 4.4 风力机连续案例：后续更快，但不能直接解释为通用记忆收益

Section 3.3 有 4 个连续风力机案例（Table 8，印刷页 132–133）：

- Case 1：复杂几何直接生成 INP，5 次自修复，22 分 20 秒；
- Case 2：使用 Case 1 的经验数据，0 次修复，10 分 27 秒；
- Case 3：基于 Case 2 代码修改，0 次修复，3 分 56 秒；
- Case 4：基于 Case 3 代码修改，0 次修复，2 分 12 秒。

作者据此报告约 90% 的时间下降，并把改善归因于经验积累和 `LESSONS_LEARNED.md`。

这里应谨慎。Case 2–4 不是独立同分布的重复任务，而是沿着同一模型逐步修改；Table 8 还明确写了 Case 2 使用 Case 1 的经验数据、Case 3/4 基于前一案例代码修改。因此，**代码复用、已验证模型继承、问题相似度和记忆文件的作用混在一起**。外部 API 延迟同样影响墙钟时间，作者也承认后续应补充 token 等指标。

所以这组结果可以说明“连续相似任务的复用路径很有潜力”，但不能作为“长期经验记忆一般能让 CAE Agent 提速 90%”的证据。

### 4.5 汇总表的边界

Table 9（印刷页 134）汇总：

| 实验 | 完成情况 | 可以支持的结论 |
| --- | ---: | --- |
| Sec. 3.1 基础自动化 | 4/4 | 在四个给定案例中能走通自动化闭环；同时暴露 intent mismatch |
| Sec. 3.2.1 未启用抑制 | 4/4 | 含糊请求即使“都能跑完”，问题定义仍可能漂移 |
| Sec. 3.2.2 启用结构化确认 | 5/5 | 固定并确认 spec 后，一个简单案例的重复性明显改善 |
| Sec. 3.3 风力机扩展 | 4/4 | 连续相似任务中，已有模型/代码/经验可被复用 |

这些都是小规模、作者自建案例，不能外推成任意 FEA 的 100% 自动化可靠性。论文也明确把非线性材料、接触、热-结构耦合、XFEM/VCCT/Cohesive Zone、UMAT/VUMAT 等列为后续工作，并指出 V&V 仍需加强。

## 5. 与本项目的对应关系

| 维度 | 论文 | 本项目当前做法 | 对我们的含义 |
| --- | --- | --- | --- |
| 缺失物理输入 | `llm_assumed` 后由用户确认 | 会改变物理模型的必需输入必须先澄清 | 保留“显式字段 + 执行门禁”，不接受未经确认的物理假设 |
| 执行工具 | Abaqus MCP 11 工具 | 3 个 typed Abaqus runtime tools | MCP 是接入方式；关键是清晰、受控、可审计的工具边界 |
| 错误反馈 | `.dat/.log` → `ERROR_CONTEXT.md` / `FIX_HISTORY.md` | raw logs、结构化 runtime evidence、API/solver evidence | 论文支持“错误证据回流”，我们继续由宿主持有原始证据与预算 |
| 自修复 | 主 Agent + 子 Agent 循环 | 单个 Pydantic AI Coder + tool loop | 论文没有证明多 Agent 是必要条件，不应据此改首轮架构 |
| 长期经验 | `LESSONS_LEARNED.md` 自动复用 | Skill/Catalog/RAG 均有各自证据和进入门槛 | 可研究经验沉淀，但应先筛选、验证、限定作用域 |
| 成功判定 | 以任务执行和结果生成为主 | execution evidence 与 host-only task oracle 分开 | 论文自己的 intent mismatch 强化了这种分层必要性 |
| 评测 | 少量案例、重复试验、连续扩展案例 | 固定 Gold / model-change cases + verifier + smoke gate | 继续用任务合同和独立 oracle，避免只报“完成率” |
| 预算/副作用 | 论文中约束较弱 | 模型/Abaqus/Solver/lookup/wall-clock 都有预算 | 论文的循环修复不能直接照搬成无界重试 |

## 6. 对当前项目最有价值的四点

### 6.1 把“需求定义正确”放在“运行成功”之前

论文最强的证据不是 100% completion，而是它亲自展示了两类失败：

- 输入含糊时，多次成功运行对应不同模型；
- 模型能成功求解，但仍可能漏几何特征或误解载荷。

这和本项目现有的 `ask_user`、missing-physics-input gate、task-specific verifier 是同一个问题的不同实现。这个方向应该保持。

### 6.2 规格本身应该成为可审计对象

`Spec.JSON` 的思想值得借鉴：把用户给定、缺失、确认后的字段显式化。我们不需要照搬其 `llm_assumed` 策略，但可以继续加强“哪些信息来自用户、哪些是任务合同、哪些是模型推断”的 provenance。

### 6.3 错误上下文应该是证据，不应该自动升级为知识

论文用 `ERROR_CONTEXT.md`、`FIX_HISTORY.md`、`LESSONS_LEARNED.md` 串起运行和长期记忆，工程上很直观，但会把“某次任务中的修复”快速变成未来上下文。

本项目更适合保持两层：

- **运行期**：保留原始错误、日志、API/solver 提示，帮助当前 Coder 修复；
- **长期知识层**：只有重复出现、作用域清楚、经过回放或评测验证的规则，才进入 Skill、Catalog 或其他知识资产。

这也能避免我们此前担心的“无止境按失败样本打补丁”。

### 6.4 连续模型修改值得单独评测

风力机实验虽然不能证明通用长期记忆收益，却说明了一个实际产品场景：用户经常不是每次从零建模，而是在**已验证模型上连续修改**。这与本项目现有 verified-seed / model-change evaluator 很接近。

因此它更像是对我们“from-scratch Gold 与 existing-model change 分开评测”的外部支持，而不是建立新 memory 系统的理由。

## 7. 不应该从这篇论文推出的结论

这篇论文不能作为以下决策的充分依据：

1. **“CAE Agent 应该改成多 Agent。”** 作者用了主 Agent + 子 Agent，但没有做同等条件的单 Agent 对照。
2. **“应该把 Abaqus 接口统一改成 MCP。”** MCP 解决互操作和工具暴露，可靠性主要来自 spec、反馈和验证过程。
3. **“`LESSONS_LEARNED.md` 已证明长期记忆有效。”** 风力机案例高度连续，存在明显代码和模型复用混杂。
4. **“系统已经能可靠自动处理通用有限元问题。”** 实验规模小，且论文明确承认高级非线性、接触、耦合、断裂和用户子程序仍未覆盖。
5. **“Solver 成功就是模型正确。”** 论文自己的中心孔板、L 形支架和悬臂梁应力结果恰好说明相反。

## 8. 对后续设计讨论的定位

这篇论文适合作为以下几个设计问题的**相关工作证据**：

- 为什么缺参澄清应位于 Abaqus 执行之前；
- 为什么需要把需求规格冻结并记录 provenance；
- 为什么运行错误需要作为结构化证据返回给 Agent；
- 为什么 execution success 和 physics / intent verification 必须分开；
- 为什么“经验沉淀”需要作用域、验证和进入长期知识库的门槛；
- 为什么 from-scratch 与 verified-model modification 应分开评测。

它不应直接改变当前“一名 Pydantic AI Coder + typed runtime tools + host verifier”的首轮架构。当前更合理的用法，是把论文作为我们现有边界设计的外部对照，并在以后讨论 Skill / RAG / 经验库时引用其正面现象和实验局限。

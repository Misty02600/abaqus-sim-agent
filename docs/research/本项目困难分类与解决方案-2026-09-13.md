# 本项目困难分类与解决方案

整理日期：2026-09-13。对象：本项目的 Abaqus 2024 单 Coder 工作流。

本文按“哪项任务能力遇到困难”组织问题，再讨论可采用的工程机制和研究方法。知识缺口识别、RAG、
案例、微调、反思和多 Agent 是解决手段，不再与专业建模、API 实现等能力并列分类。

核心建议是：先让限定任务中的要求、建模决定、实际模型和独立验收连起来；在这条链上定位失败，
再决定补文档、补规则、提供中间表示、训练模型或拆分工作流。这个建议允许研究不成熟方案，
但不把它们直接变成产品默认配置。

本文是方案比较与研究建议，不是实施计划或已采纳架构决定。没有修改产品代码、调用模型、运行 Abaqus，
也没有复现第三方实验。项目现状依据当前项目约束、既有分析和历史评测；没有重新审计全部源码或原始轨迹。
详细项目证据见[困难点与证据分析][L1]，此前论文与固定源码核查见[原文核查][L2]。

## 一、先把分类和成熟度分开

### 1. 六类能力困难，加一条横向知识机制

这里用 A—F 标识新分类，避免与原十二项问题编号混淆。同一失败可以关联多类，但应先定位主要失败环节。

| 分类 | 要解决的核心问题 | 对应原问题 | 典型失败 |
|---|---|---|---|
| A．需求理解与工程意图 | 用户究竟要研究什么，哪些输入已知，哪些需要澄清？ | 1 | 把示例材料常数当作本次试样数据；忽略新要求 |
| B．专业建模与数值判断 | 应采用什么物理假设、材料/界面描述、单元和数值策略？精度够不够？ | 2、3 | API 合法，但建模假设不适用；只划网格而不检查目标量精度 |
| C．模型实现与 API 正确性 | 建模决定是否正确转成脚本、实际区域、属性及输出？ | 4、7 | 选错面或实例；对象归属错误；把输出分量绑定到错误字段 |
| D．错误诊断与修复收敛 | 能否在预算内根据新证据修复，同时保持工程要求？ | 8 | 重复试错；探针成功却未修改正式脚本；靠改变问题消除错误 |
| E．执行与状态可靠性 | 文件、会话、任务修订和外部 Job 是否对应同一次任务？ | 10；关联 12 的配置部分 | 重复提交；旧结果冒充新结果；恢复后预算或证据错位 |
| F．独立验收、评测与能力边界 | 怎么证明正确、评价改进，并界定可以对外宣称的能力？ | 9、11、12 | 运行成功被当成物理正确；验收器放过错误模型；小样本被外推 |

**横向 K：知识缺口识别、查证与证据利用，对应原 5、6。** 它服务于各类能力，重点支持 B 和 C。
例如，不懂某单元的适用条件属于 B；没有发现需要查证，或没有拿到正确条件，则是 K 环节的问题。
不需要为此新增一个分类 Agent，评测时对现有 Coder 轨迹进行标注即可。

“不知道”还应进一步区分：

| 缺少的东西 | 例子 | 应获得什么 |
|---|---|---|
| 用户事实 | 试样厚度、材料试验数据、真实装夹方式 | 用户或可信文件提供的事实；必要时澄清 |
| 领域或接口知识 | 单元适用条件、API 对象归属 | 版本与条件匹配的资料、规则或案例 |
| 理解与组合能力 | 条件已给全，仍不会把它们组合成方案 | 更清楚的中间产物、规划支持，或有针对性的训练 |
| 当前任务的数值证据 | 这张网格对本次目标量是否足够 | 实际计算、误差分析或独立参考，不能仅靠检索补齐 |

这是一套本项目的分析划分，不是宣称行业存在同名统一分类标准。

### 2. “成熟”描述的是具体机制及其边界

| 本文用语 | 判断依据 | 不意味着什么 |
|---|---|---|
| 成熟做法 | 有正式软件功能、明确工程规范，或能确定实现并验证的局部机制 | 不代表组合后的自主 CAE Agent 已达到工业交付水平 |
| 研究验证 | 论文有相关实验，或项目有局部实验；任务、数据和配置有明确范围 | 不代表跨软件、跨物理问题仍有效，更不代表稳定生产成功率 |
| 探索构想 | 论文展望、原型方向或本文提出的迁移设计，缺少对应任务的充分证据 | 不是无参考价值，但不能作为已有能力或默认采用依据 |

同一种技术可以有不同层次：结构化字段校验是成熟机制；从任意工程描述中正确生成这些字段仍有研究难度。
微调的训练流程可实施，也不等于训练后能自主选择正确物理模型。

另外单独记录本项目状态：**已有实现、默认关闭的实验配置、尚未实现、只有历史观察**。
“外部有成熟机制”“仓库里有代码”“本项目任务有收益”是三个不同结论。

## 二、A 类：需求理解与工程意图

### 困难与项目现状

首先要区分用户事实、建模决策和实现细节。例如，“材料数据在文件里”应先读取；“这个 API 怎么调用”
不应交给用户决定；“本次采用何种真实界面行为”不能由相似案例替代。用户后来修改载荷或目标量，
还需要确定哪些旧要求继续生效。

项目已有 `needs_input` 和按工作区事实优先处理的交互策略。历史六场景中出现了合理零检索和缺材料参数时
正确澄清的正例；这不证明所有信息冲突、多材料表和多轮任务都已解决。[项目依据][L1]、[行为记录][E1]

### 成熟做法：任务规格、来源记录和有条件澄清

建议针对准备支持的任务家族，保留一份紧凑的任务规格：研究目标、单位约定、几何与材料输入、载荷与约束、
已确认假设、目标输出和验收要求。每个关键值注明来自用户、可信文件、明确推导，还是任务允许的假设。
其中字段和来源校验可确定实现；从自然语言提取字段的正确性仍需检查。

工程上先规定用途与验收标准，再进行模型开发和评价，可以参考 NASA-STD-7009B 的建模与仿真可信性框架。
本项目借用的是用途、验收和证据相互对应的方法，不声称符合或获得该标准认证。[S1]

对本项目的最小方案是：先复用已有请求和修订记录，只补当前任务验收确实需要的信息。读取到冲突时指出
具体冲突；必需事实缺失时询问最小必要问题；任务已允许的实现选择由 Coder 自行处理。无需要求用户确认
每一条 API 或所有中间步骤，也无需建立庞大的通用工程本体。

### 研究验证：把描述转成可检查的建模规格

MCP-SIM 展示了将描述逐步结构化的路线，但其澄清机制包含推断缺失信息，不能等同于向用户确认事实。
可借鉴的是信息组织；对真实材料和边界的自动估算不适合直接迁移到本项目。[S6]、[既有补充材料核查][L2]

### 探索构想与验证

可以研究“决策影响导向的澄清”：只有当不同答案会改变物理模型、验收或不可恢复动作时才追问。
也可以让系统保留两个明确标注的候选解释，先用现有文件消除歧义。这里尚没有本项目效果证据，
不能把模型自报的置信度直接设成可靠门限。

验证应使用完整输入、文件中有值、关键值缺失、来源冲突和用户修订等成对任务，分别检查漏问、乱问、
补造参数和变更遗漏。正确澄清可以完成澄清题，但不能记成已经完成一项完整仿真任务。

## 三、B 类：专业建模与数值判断

### B1．物理假设、材料/界面描述与单元选择

**先判断什么。** 决策顺序应围绕工程目的：目标响应与适用假设 → 几何和材料/界面表示 → 分析过程 →
单元与离散策略。不能只训练“看到薄结构就输出某个单元名”。材料模型名称、参数的真实性和参数适用范围
也必须分别检查。

**项目现状。** 已有板任务允许在 CPS4/CPS4R 中选择，但仍固定 80 个单元。两批结果合计是 3/6 的历史观察，
包含 Provider 超时；它支持限定选择的局部正例，不支持任意二维/三维、超弹性或界面模型的自主选型。[E2]

**成熟做法：把专业经验限制在可审定的任务范围。** 建议先维护少量由工程人员核查的“建模方案卡”：
适用前提、排除条件、必需数据、允许的实现、重点检查量和参考案例。对选定问题族，先让人审定规则和
参考实现，再由程序检查可机械判定的兼容条件。这里成熟的是受限规则与参考流程的管理，
不是所有工程判断都能转成完备规则。

例如可以先规定一类已有解析或可信参考的线弹性问题；用户要求超出该范围时，输出尚未验证的部分或询问，
而不是继续沿用模板。项目已有的 verified seed 可作实现起点，但不能成为新物理假设成立的证明。[L1]

**研究路线一：完整案例与结构化领域知识。** AbaqusAgent 提供问题说明、元数据及完整 INP 案例，
用来展示模型各定义之间的配合；ChatCFD 则把文件依赖、边界条件、量纲和求解器模板等组织成专门知识。
前者提醒我们提供完整上下文，后者提醒我们表达兼容关系。[S4]、[S5]

对本项目的候选迁移是：围绕已有 Abaqus 主知识源提供“条件—决定—验证方式”的证据单元，
再链接经过核查的案例片段。相似度只负责找到候选，不承担物理适用性判断。不需要因此另起一套互相重复的语料。

**研究路线二：领域微调。** ALL-FEM 使用专家与筛选后的合成 FEniCS 代码进行微调，并结合执行反馈。
它证明了一条值得研究的专业代码训练路线；其中部分题目已给定建模假设和网格，不能把成绩全部解释成自主选型。
本文使用 arXiv v1 方法证据，不复用该版本存在口径疑问的总成功率。[S7]、[L2]

本项目只有在“资料已正确送达、仍反复不会组合或实现”的留出任务上，才有充分理由进一步比较微调。
训练样本建议保留需求、适用条件、决策、执行证据及错误修正；只收集可运行脚本会遗漏判断依据。
成本主要是专家审核、可信执行标签和按问题族隔离的数据，不能只按训练算力估计投入。

**探索构想。** 对少量存在多个合理方案的任务，可让 Coder 提出候选，用低成本参考计算筛掉明显不合格者；
也可研究使用独立验收信号训练选择策略。这两条都是本文候选设计，尚未在本项目验证。
便宜的筛选模型本身可能不适用于目标问题，不能让它成为隐藏的新假设。

**怎样验收。** 同一任务分别给定完整方案和只给工程要求，比较选择、理由、实际模型与结果是否一致；
另改变一个决定性的物理条件或目标量，检查方案是否合理改变。允许多种合格单元或模型表达，
不要将参考脚本中的唯一字符串当作所有正确方案。

### B2．网格、增量与数值充分性

**成熟做法：误差指标、受控细化和目标量验证。** SIMULIA 的官方课程明确介绍 Abaqus/CAE 与
Abaqus/Standard 联合进行基于误差指标和网格尺寸目标的自适应重划分。Ansys Mechanical 也提供
基于选定结果与误差指标的自适应收敛功能。这说明相关数值工具已有软件实现，Agent 不必凭语言直觉
发明整套网格策略。[S2]、[S3]

这些来源不保证所有分析都适用。Ansys 文档列出材料、非线性和其他功能组合的限制；SIMULIA 课程简介
也不等于本项目已核查 Abaqus 2024 的全部支持矩阵。不能据此直接承诺柔性基底、接触或界面损伤都可自动重划分。

建议先定义目标量 Q、取值位置或区域、误差容限和最大计算成本，再选择适用的细化方法。
初始网格可由受审定的案例或经验给出，充分性则由实际计算检查。一个候选变化指标是：

`delta_Q = abs(Q_fine - Q_coarse) / max(abs(Q_fine), Q_scale)`。

这里的 `Q_scale` 和容限应事先约定，避免近零值扭曲相对变化；这个表达式只衡量相邻结果变化，
不是连续真解误差的保证。需要检查细化序列、几何和物理设置一致性，必要时结合独立参考或误差估计。
固定步数、固定两张网格或一个通用百分比都不应自动成为充分性标准。

**研究路线：Agent 负责提出策略，数值工具负责提供证据。** 可让它解释要细化哪里、为什么、下一次计算
要排除什么疑问，再由确定性统计记录 Q、误差指标、网格规模和成本。实际网格必须由求解产物或模型读取确认，
不能采信报告中的自报数量。这是本项目迁移建议，尚未实现自主精度闭环。

**探索构想：从几何语义辅助网格决策。** 可以研究多视图几何观察、候选热点定位和学习型细化策略，
但图像上的“看起来危险”需要映射到实际区域并接受数值比较。ChatCFD 在未来工作部分讨论了几何、网格、
求解、优化 Agent 的衔接，并提供应用入口；该展望与文中受测的、需要已有网格的主流程应分开，
不能把架构图当作任意网格精度已有保证。[S5]

**本项目的落地与验收。** 先在一个允许改变网格、目标量明确且有参考证据的题族中比较：固定人工策略、
程序化细化、Agent 选择细化。统计达到要求的成本、错误宣布充分的次数、预算耗尽后的报告是否诚实。
预算不足时应区分“已完成当前求解”和“尚未确认目标精度”；沿用现有终态承载说明即可，
本文不增加新的产品状态枚举。

## 四、C 类：模型实现与 API 正确性

### 困难与项目现状

这一类有两个相邻层次：API 是否合法，以及合法操作是否落实了正确的模型含义。
对象可以访问，不代表它属于目标实例；集合非空，不代表选中正确加载区域；输出读取成功，
不代表读对分量、帧和工况。

项目已具备 API Catalog、运行错误证据、固定任务模型检查，以及特定配置下的静态预检和窄范围编辑保护。
这些机制各有启用条件。已有 B31 输出合同错误与修正记录，说明具体接口知识值得精确补足；
窄编辑保护则只证明改动范围，不能替代模型语义验证。[L1]、[E7]

### 成熟做法：分层检查，加少量稳定适配

建议把检查分成三层：语法与已验证接口约束；对象、区域和输出合同；本次实际模型和结果。
第一层尽量确定性执行，第二层针对支持的任务族定义可检查条件，第三层独立读取实际产物。
不需要把 Abaqus 全部 API 强类型封装；可只稳定封装高频且已复现的问题，例如结果提取或易混淆对象的访问，
其余仍保留普通 Abaqus Python。

工业软件已有可编程对象模型与远程执行接口。PyMechanical 官方文档区分嵌入式对象访问与 gRPC 远程控制，
可作为“把软件操作做成明确执行边界”的参考；它并不证明调用者理解工程问题，也不是建议将本项目改成 Ansys。[S10]

对本项目而言，新增检查优先回答“实际区域在哪里、属于谁、覆盖了什么、用了什么属性”。
几何变化后重查区域含义，避免把固定面编号当作永恒身份。若某项关键属性无法读出，应标记尚未核实，
不能把未发现异常视为通过。这些任务语义检查需要逐族开发，不能泛化为完整 CAE 验证器已经存在。

### 研究验证：可检查的中间表示

二维框架多 Agent 论文先组织节点和连接关系，再生成 OpenSeesPy。其消融在有限框架族内发现，
即使规则与模板信息相同，合并几何与代码生成也会出现可执行但几何错误的结果。它支持检查中间产物的价值，
不证明角色越多越好。[S8]

本项目可以由同一个 Coder 输出紧凑的区域、连接、材料赋值或输出意图，再与实际模型对照。
这种中间说明用于检查，不取代动态脚本，也不要求将整个 Abaqus 建模空间先编码成固定 DSL。
真正成本在于把说明映射到可观测模型事实；只增加一份模型自己填写的 JSON 不会自动增加可信度。

### 探索构想与验收

多视图观察和 VLM 可辅助检查几何、网格、边界区域是否明显选错；更进一步可以研究“自然语言区域名称 →
模型实体”的语义映射。不过，视觉检查可能漏掉遮挡、内部属性和数值设置，应作为辅助证据。
该迁移目前没有本项目验证记录。

验收应分别植入错误对象归属、错误实例/端面、错误材料区域、错误输出分量，并保留合法的不同脚本写法。
同时考察正确模型被误拒的情况。API 正确率、模型语义正确率和最终任务通过率应分开记录。

## 五、D 类：错误诊断与修复收敛

### 困难与项目现状

项目已观察到修复长尾：B31 某失败轨迹用了 31 次模型请求、12 次 Abaqus 调用，却没有进入 Solver。
文件 allowlist 有助于限制执行范围，但不自动减少无效推理。已有预算和实验性探针协议也不能直接当作
任务收益证据。[E8]、[L1]

### 成熟做法：有界执行反馈、正式改动和回归检查

保留原始日志和结构化错误，不让解释或检索覆盖原始执行状态；明确下一次动作要检查哪个假设；
记录正式脚本的改动及其对应证据；重跑后复查受影响的工程要求。次数、求解成本和总时间由宿主限制，
不依靠模型自行决定何时结束。

本项目应继续保留报错后的自动证据增强，同时核对这次 profile 是否启用。对已知 API 错误优先交付
精确对象关系或运行注释；对 Solver 诊断提供适用资料，但不能把某条警告机械映射成唯一物理根因。

历史 B31 梁弯曲中，明确该任务写端/读端输出合同后，三次记录的 Abaqus 调用均为 3，原 control 为 8、9、6。
这是局部组合方案的改善线索；样本少且同时补了多项信息，不能归因某一句提示或推广到全部输出。[E7]

### 研究验证：反思记忆和经验采用

Reflexion 将任务反馈转成文字经验，放入后续尝试的上下文；它不通过这一步更新模型权重，
原文也承认效果依赖反馈和自评质量，没有成功保证。[S12]

迁移到本项目时，更值得试验的是“错误 → 经验证的结论 → 正式脚本采用 → 独立回归”的链条。
如果只保存模型的解释，错误归因可能作为经验反复传播。跨任务写入 Skill 或 Catalog 前应经过独立核查，
保留版本、适用对象和反例；本项目当前探针协议并不授权自动写入跨 run 知识。[L1]

### 探索构想与验收

可以研究按“预期新增信息/运行成本”挑选下一次诊断动作，或者比较少量候选修复。但收益需要与多花的预算、
误停止和上下文成本一起计算。仅凭错误文本相同就永久禁止重试也可能误伤环境已经改变的任务。

建议在固定真实失败家族里测：首次正确修复、总调用与长尾、重复错误、诊断结论进入正式产物的比例，
以及工程要求是否保持。降低目标载荷、替换用户要求的界面行为或放宽精度来换取运行通过，
应作为候选错误注入检查；本文不宣称这些行为都曾在项目中发生。

## 六、E 类：执行与状态可靠性

### 困难与项目现状

需要对齐四件事：用户当前要求、会话中的步骤、工作区实际文件、外部进程实际状态。
项目已有文件后端恢复、累计预算、任务修订和新证据基线；未知在途 Abaqus 调用进入 `needs_reconcile`。
已有会话续跑不等于已有外部 Job 重附着或 exactly-once。[L1]

### 成熟做法：持久身份、幂等操作和外部状态核对

可靠工作流应为任务修订、输入、操作和产物保留关联身份，恢复时核对已经完成和仍未决的动作。
可以恢复聊天历史，不意味着可以安全地再次提交一个外部 Job。

Temporal 的官方 Activity 文档明确要求可重试活动具有幂等性，并讨论“外部动作已发生但完成记录未写入”
时的重复执行。这是外部副作用处理的成熟参考；采用工作流框架也不会自动让 Abaqus 提交具备恰好一次语义。[S11]

当前最小方案是保留已有失败关闭边界，并加强任务修订、已完成步骤复用和产物归属检查。
只有确实需要后台长作业或重附着时，再独立设计 Job 身份、查询、取消、人工或程序核对和重复提交防护。
不因本轮分类引入 Temporal、数据库或新的调度框架。

### 研究或探索部分

复杂任务中，“旧任务的哪些计算仍可用于新目标”具有语义判断成分。可以研究依赖关系记录与 Agent 辅助
复用建议，但最后是否接受旧产物应由明确的输入和验收条件决定，不能靠模型说“应该一样”。
自动恢复未知在途 Job 目前仍是本项目未实现的方案方向，而非现有能力的重新命名。

这一类不必为了分类对称而强找新论文：大量问题已有明确的软件工程解法，难点是与 Abaqus 的真实副作用
正确对接。应在文件已完成、CAE 已完成、Solver 未决、任务被修订四类切点注入中断，验证合理复用、
必要停止和新证据建立；不是所有切点都应自动继续。

## 七、F 类：独立验收、评测与能力边界

### 困难与项目现状

项目已明确区分普通 CLI 的 `execution_evidence` 与固定评测的 `task_oracle`。
前者验证执行证据，后者才检查任务专属物理要求。这条职责边界应保留，不能把开放编码入口描述成
已经覆盖开放工程问题的物理验收。[L1]、[ADR-0019][L4]

历史梁弯曲的旧验收器曾接受合同不允许的额外输出，严格回放使一个旧 treatment 的 3/3 变成 1/3。
问题已修正；它提醒我们验收器本身也必须接受检查。[E7]

### 成熟做法：先区分算对方程、数值充分和模型适用

NASA-STD-7009B 区分实现/数值方面的验证与模型针对实际对象的确认，并要求记录适用范围。
把这套方法迁移到本项目，应分别问：执行是否完成、离散与数值结果是否可信、模型是否能够回答目标问题。
其中某层通过不能替代其他层。[S1]

建议对每个受支持任务族，维护公开任务合同、独立参考依据和宿主验收。先在已有五层框架下检查：
需求忠实度、实际模型语义、规定求解过程、目标量正确性、任务级成本与稳定性。[既有设计][L2]

参考依据可以是解析结果、受审定的数值参考或实验；不同来源承担的证明责任不同。
模型自己写出的测试可提供候选，但隐藏参考与最终判定不由同一生成过程自行定义。
开放问题没有充分参考时，应明确报告已验证与尚未验证的内容，不把“没有报错”变成默认通过。

### 研究验证：专门测试验收器和知识依赖

FEM-Bench 将辅助函数支持程度与任务组合难度分开，并要求生成的测试同时放行参考实现、拒绝预设错误实现。
可借鉴的是辨别能力测量；它测计算力学代码任务，不是完整 Abaqus Agent。[S9]

对本项目，可先准备正确参考和错误变体：错误材料区域、错误载荷、旧 ODB、缺少最终加载、错误结果分量。
还要加入物理上合格的替代实现，统计误接受与误拒绝。错误变体检测率只说明对这组变体的能力，
不是生产环境整体漏检率。

### 探索构想：自动生成验收与多层评审

可以让另一个模型提出检查项，或用多个专业角色审查不同环节；也可以从工程规格生成候选验收脚本。
但新脚本必须先接受正确/错误对照检验。模型间相互同意、模型自报高置信度，都不能代替独立物理证据。
把“自动生成检查”发展成“可靠自动验收开放任务”，仍需要额外验证。

### 本项目评测应怎样设计

先沿用已有 A/B/C/D 瓶颈定位实验设计：基础条件、选定知识增强、人工匹配证据、再加工程师方案。
这里的 A/B/C/D 是实验条件名称，与前面的能力分类不是一回事。[L2]

如果人工证据显著改善，就追查查询时机、语料、排序、片段和应用环节；如果还需工程师方案，
再看规划与知识组合；给了方案仍失败，则检查 API、实际模型观察、执行和环境。它们是诊断线索，
不能直接推出唯一因果。人工辅助条件不混入自主 Agent 分数。

Generic Harness 的 CAE 研究通过对照教程使用方式，提示知识条件会改变结果；其中跨系统比较并非所有
模型与判分都严格一致。因此本项目比较框架、检索或多 Agent 时，应先固定模型、知识、预算和验收口径。[S13]

任务按物理/几何家族留出，报告逐题重复、失败原因、人工介入和运行成本。保留全部启动数，
Provider 无效可在行为分析里单列，但不能从用户视角的任务结果中消失。少量 2/3 或 3/3 仍是 smoke 证据。

## 八、横向 K：知识缺口识别、查证与证据利用

### 1. 先确定缺口在哪一层

建议按以下链条回看失败，不用“模型不主动 RAG”解释所有问题：

`需要依据的决策 → 是否发现需要查证 → 问题表达 → 语料覆盖 → 检索排序 → 完整证据送达 → 适用性判断 → 实际采用`。

本项目有直接案例：正确章节已在索引中但没有进入返回集合；长标题挤占正文预算；普通词被当作符号；
文档产品范围混入；正确代码配了不适用的解释。增加文档、扩大 Top-K 和更换融合算法分别只可能影响
其中一部分，不是通用补救。[E1]、[E3]

### 2. 可用手段及成熟边界

| 手段 | 具体解决什么 | 成熟度与本项目取舍 |
|---|---|---|
| 精确 API 查询与已验证运行注释 | 方法、参数、对象归属、已复现行为 | 查询机制可实施，项目已有；是否改善任务要按具体 profile 评价 |
| 版本/产品范围和完整证据交付 | 避免适用条件丢失、对象混淆和片段截断 | 属于可确定修复的检索工程；优先针对已观察缺陷 |
| 受审定的建模规则与完整案例 | 补充适用条件及跨步骤组织方式 | 小范围知识可审核维护；自主迁移仍需研究验证 |
| 按需检索和显式证据回评 | 判断何时查、资料是否足够、是否需要补查 | 项目有行为正例，也有协议失败；不能把强制流程视为成熟默认 |
| 领域微调 | 改善反复出现的专业表达、实现或组合困难 | 训练可行，目标能力增益仍需留出任务验证，不能替代用户事实 |
| 经验记忆或 Skill 归纳 | 避免重复已解决错误 | 持久化容易；可信经验提炼和跨任务适用性仍需审定 |
| 多 Agent 分工 | 分离长上下文、不同观察或独立检查职责 | 编排可实现；提高专业正确性的效果应由同条件实验支持 |

### 3. 研究方向：学习查证策略，不等同于加一句提示词

Self-RAG 通过训练反思标记控制检索，并评价相关性、支持程度和输出质量；其实验针对知识密集型语言任务。
这不是把普通模型提示成“先反思一下”就完成了同一方法，也不是已经解决 Abaqus 的知识缺口识别。[S14]

对当前项目，更低成本的候选是先用离线轨迹检查“该查、可不查、该问用户、证据不足应停止”四类行为，
再比较提示、工具描述和少量显式门禁。若未来训练查证策略，仍需独立标签和任务结果评价，
不能用工具调用率当成功指标。

已有 `bounded_v1` batch-2 的 3 通过、4 行为失败、1 Provider 无效，尚未获得行为资格；
其中没有 Abaqus 和 live ranking 查询，也存在当次配置混杂。它应继续作为需解释的实验记录，
不能因为策略形式更完整就升级为默认路径。[E4]

### 4. 对现有知识设计的具体建议

继续保持一个主 Coder、Abaqus 主知识源、精确 API 与文档两个主动入口，以及按配置启用的报错自动证据。
不新增分类 Agent，不为每个 API 建强类型业务封装。

先修已知证据链问题，再决定是否需要额外材料。已有文档知识应保留来源、版本、产品、对象范围和关键条件；
自动提炼的规则先作为候选，不能无验证进入可信 Catalog。2026 FD02 资料与 2024 执行目标的差异必须保留，
不能由“官方来源”标签消除。[L1]

RRF 相对 Dense 的已有 held-out 只净多命中一题，不能据此要求切换默认方案。[E5]
也不应要求每一步必查：本地事实和知识已足够时，零查询完全可能是合理行为。

## 九、对本项目的方案组合与选择顺序

下面是取舍建议，不新建 TODO，也不把尚未验证方案标成已采纳。

### 1. 近期最有根据的组合

**任务规格与来源 + 已有单 Coder + 按需知识与错误证据 + 任务相关模型检查 + 独立验收与预算。**

这组方案尽量复用现有边界。新增工作重点应是让某个支持题族的工程要求能被实际检查，
并消除已有检索/API 错误链中的具体缺陷，而不是同时开启所有实验功能。

| 工作方向 | 主要产物 | 可以证明什么 | 主要代价 |
|---|---|---|---|
| 对齐一个题族的要求与验收 | 有来源的输入、公开交付合同、参考实现和错误变体 | 能区分正确实现、缺输入、错误模型和验收器问题 | 工程审定与 oracle 编写 |
| 修补已观察的知识/接口链 | 完整适用证据、精确输出合同、局部回归 | 已知错误不再由相同缺陷反复触发 | 文档核查、版本维护与受控回放 |
| 补充实际模型语义检查 | 区域、属性、输出与任务修订的对应证据 | 正确决定确实落实到了模型 | 逐任务族的观察与判定实现 |
| 独立开展自主选型/精度实验 | 与给定方案和固定策略匹配的成对结果 | 把专业判断能力与脚本执行能力分开 | 真实仿真成本、独立参考与重复试验 |

### 2. 哪些研究方案在什么条件下值得进入下一轮

| 已得到的证据 | 值得比较的方案 | 不应立即推出的结论 |
|---|---|---|
| 正确知识未送达，送达后可以完成 | 改查询、证据组织、案例检索或查证策略 | 必须训练更大模型 |
| 正确证据已送达，仍不会形成方案 | 中间建模步骤、受限规则、候选方案比较、领域训练 | 加一个“专家 Agent”必然解决 |
| 方案正确，实际几何/区域经常实现错 | 模型状态观察、可检查中间表示、局部适配器 | 必须把全部 Abaqus 改成固定 DSL |
| 主要失败来自重复诊断和未采用结论 | 有界反思、诊断结论采用检查、经验审定 | 单纯增加重试预算就能收敛 |
| 主要问题是未知在途 Job | Job 身份、状态查询与恢复设计 | 换 Harness 就自然获得 exactly-once |
| 运行大多成功，但物理错误仍被接受 | 加强合同、参考依据和验收器错误注入 | 继续优化运行通过率就足够 |

### 3. 一项贴近研究场景的候选任务

以后扩展到金属导线/柔性基底时，可先把“改变导线宽度并比较指定路径应变”作为候选研究题，
并明确材料、界面、加载和允许的假设。它在当前文档中只是扩展场景，不代表已支持该非线性闭环。

A 类核对数据来源和修改目标；B 类审定模型表示与目标量，并安排数值充分性检查；C 类检查宽度、
区域、属性和输出确实落实；D 类防止修复时改掉原工况；E 类绑定新修订与产物；F 类用受审定的参考及
变更回归检查结果。知识机制在缺少依据时介入，而不是成为新的固定步骤。

这项题只有在所需材料和界面数据、数值参考与验收办法准备好后，才适合用于能力评价。
准备期间可以先用已有线性题族验证同样的证据链，避免把尚未建立参考解的问题直接交给 Agent 自证正确。

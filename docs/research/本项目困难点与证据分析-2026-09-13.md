# 本项目困难点与证据分析

核查日期：2026-09-13。对象：本仓库的 Abaqus 2024 单 Coder 产品路径及其固定任务评测。

本文按六类能力困难和一条横向知识机制组织原十二项分析，保留原编号、逐项内容与证据入口。
成熟做法、论文中的研究方案及探索构想，统一见[困难分类与解决方案](本项目困难分类与解决方案-2026-09-13.md)。
这次分类重排没有重新运行模型或 Abaqus，也没有扩大下述历史核查范围。

本项目需要解决的核心问题，是把用户的工程意图连续、可靠地落实为建模选择、实际模型和可验证结果。
这包含专业判断，也包含软件接口、外部运行和验收责任；任何一层正确，都不能代替其他层的证据。

目前有直接历史证据的薄弱处，主要是 API/输出合同理解、检索证据交付、修复长尾和 Provider 中断。
自主建模选型、自动判断网格充分性、开放任务物理验收，则主要属于尚未充分验证的能力范围。
不能根据现有记录断言“模型专业知识不足就是最大的瓶颈”，也不能因为固定算例通过就认为这些问题已经解决。

## 阅读与证据边界

本文是在既有研究基础上对本项目的应用分析，不重新开展行业调研。第三方工作的依据、工程意图核查方法、
错误注入场景和 A/B/C/D 对照设计，见[专业能力与工业评测原文核查][R1]的第三至第五节。

本次读取了项目约束、相关 ADR、选定的 benchmark JSON，并抽查当前 Coder 装配、请求合同、提示词、文档工具、
执行验收及恢复入口。未逐条重读所有原始运行轨迹，未全面审计源码，也未重新调用模型、Abaqus 或复现历史实验。
下文中的次数、通过数和具体历史错误来自所链接的报告；源码抽查只用于确认当前职责和接口边界。

四种证据用语如下：

| 用语 | 本文含义 |
|---|---|
| 历史已观察 | 指定日期、任务和配置下记录过的问题；不自动表示当前版本仍可复现 |
| 已有防护 | 当前代码或已采纳 ADR 有对应机制；实际模型是否受益要另看评测 |

## 先对齐当前项目形态

当前产品是一个 Pydantic AI Harness Coder `abaqus_2024_coder`，编写普通动态 Abaqus Python。
常规运行路径通过 `run_cae_script`、`run_solver_job`、`run_abaqus_python` 分别建模、求解和提取结果；
通用 Shell 被移除。ADR-0023 的纯编辑模式是例外：它不注册这三个运行工具，只允许显式合同中的窄范围编辑。
这里没有已经运行的分层多 Agent，也不要求用固定 DSL 或确定性 renderer 替代普通脚本。[产品范围][P1]、[装配源码][P2]

Agent 只能返回 `needs_input`、`ready_for_verification` 或 `failed`。最终 outcome 由宿主决定。
普通 CLI 的 `execution_evidence` 检查声明交付物的存在与 freshness、Python 3.10 语法和已使用阶段的最后一次执行证据；
固定 evaluator 的 `task_oracle` 才进行任务专属物理验收。前者允许开放编码任务，但不证明开放工程问题正确。
这是已明确的产品范围划分。[ADR-0019][P3]、[执行验收源码][P4]

API Catalog、文档检索、Solver advisory、静态强制检查、查证协议和编辑范围合同等，有显式配置和默认关闭的实验路径。
分析某次行为时必须看该次 request/launch/profile，不能把“仓库里有这个功能”当作“所有任务都启用且已经有效”。

## A．需求理解与工程意图

### 1. 不知道的是用户事实，还是可以自行解决的建模与实现问题？

**困难在哪里。** 用户可能只在消息中说“按已有模型计算”，材料、单位和边界条件却在工作区文件里。
反过来，脚本里存在一个数值，也不代表它就是当前试样的有效参数：它可能来自旧任务、示例或其他材料。
Agent 要判断信息是否存在、来源是否适用于当前任务，以及缺少它是否会实质改变模型。

需要分开的至少有三类问题：

| 信息类型 | 具体例子 | 合理处理 |
|---|---|---|
| 用户或试验事实 | 本次试样厚度、材料实测数据、实际加载方式、采用的单位体系 | 读取可信文件；仍缺失或冲突时澄清，文档不能替用户赋值 |
| 工程判断 | 是否需要考虑某种非线性、某种简化是否满足目标 | 根据已知任务和适用条件判断；存在改变物理问题的歧义时澄清 |
| 实现问题 | 集合实际叫什么、API 属于哪个对象、字段如何访问 | 查工作区、API 和运行证据，不把软件细节转交用户决定 |

**项目已有处理。** 当前提示词区分 `legacy` 与 `workspace_facts_first`。后者允许先读工作区事实，
但在关键事实仍缺失时，禁止继续编写依赖臆测值的模型或执行相应工作。它也明确不应让用户替 Agent 选择 API。
2026-09-05 的六场景记录中，两项任务正确复用本地事实而未检索；缺少弹性模量的场景询问了数值和单位。
该场景因为脚本化回答方没有答案而形成 clarification 终态，不应按“模型没有正确澄清”计错。
[提示词源码][P6]、[文档工具行为记录][E1]

**剩余困难。** 目前主要依赖模型执行这些语义要求。尚不能据此证明它能可靠处理多个材料表、混合单位、
旧脚本与新要求冲突，或者“名称相同但适用对象不同”的信息。固定 Gold 的首动作澄清规则也不能直接拿来评价
允许先读文件的新交互策略。

**有区分力的检查。** 同一任务分别把必需参数放在消息、工作区、相互冲突的两处和完全缺失的情形中。
观察它是否在前三种情况下正确定位或发现冲突，在真正缺失时提出最小必要问题；同时检查它是否擅自引用模板值。
这比单独统计“问了多少次问题”更能说明任务理解能力。上述组合尚不是本文新执行的测试。

## B．专业建模与数值判断

### 2. 会调用建模命令，不等于会选择合适的工程模型

**困难在哪里。** “选单元、选属性”不是同一层决策。需要先明确要描述的物理行为和允许的简化，再选择
对应的模型表示、材料或界面描述，最后才落实到单元、section 和 API 参数。即使调用完全合法，选择仍可能
不适合用户关心的量。

例如，若以后扩展到柔性基底、细导线、接触或界面损伤任务，需要分别回答：目标是整体刚度还是局部响应；
用户要求保留哪些几何和变形行为；材料与界面数据是否足以支持拟采用的描述。这里是候选扩展场景，
不是现有 plate/bar/beam 记录已经验证的能力，也不是建议自动替用户补齐材料参数。

**项目已有证据。** 自主选择单元的板任务允许 `CPS4` 或 `CPS4R`，仍固定为 80 个单元。
2026-09-03 的时间分离复测中，两个成功 run 分别采用 80 个 CPS4R 和 80 个 CPS4，并通过该任务的完整宿主 oracle。
新批次为 2/3，前批为 1/3；两批只能合并描述为 3/6 的观察，失败包含 Provider 超时。
这是“在明确适用范围内选择不同实现”的正例，不能外推为能自主决定二维/三维、材料模型或任意单元家族。
[单元选择复测报告][E2]

**剩余困难。** 项目尚缺少能把“遵循给定方案”和“自主完成专业选型”分开的充分证据。
只检查最终 element type 是否属于两个允许值，无法说明模型是否理解选择依据；只听模型解释，也无法证明解释
真正指导了代码和模型状态。材料模型名称的正确性还不能替代其参数的来源与适用性。

**有区分力的检查。** 构造由工程人员审定的成对任务：外观和措辞相近，但某个明确的物理条件或目标量改变，
因而应改变某项建模选择。验收“选择—理由—实际设置”是否一致，并允许多种满足要求的方案。
关键不是让 Agent 总给出唯一型号，而是分清哪些选择受物理约束、哪些只是等价实现。

### 3. 划出网格、求解完成和数值充分性，是三个不同问题

**困难在哪里。** API 知识可以帮助生成网格，却不能仅凭一个通用网格尺寸证明目标结果足够准确。
需要先知道用户要比较什么量、在哪里取值、允许多大误差，再判断是否需要细化和追加计算。
求解器完成当前离散问题，也不自动证明该离散化足以回答工程问题。

**项目已有处理。** 现有 Gold 和部分模型修改任务对单元数量、拓扑、输出与数值结果有固定检查。
例如单元选择复测固定 80 个单元，双材料修改任务检查分区、材料赋值和共享节点等任务状态。
这些证明 Agent 能在规定离散化和验收范围内构建模型，不能证明它能自主设计网格充分性检查。
[单元选择报告][E2]、[模型修改 suite][E3]

**剩余困难。** 至少包含三个尚需明确的接口：目标量由谁定义；数值充分性由什么独立证据判断；
预算不足以继续检查时如何报告“已求解，但精度未确认”。如果不先定义目标量，所谓“网格收敛”可能只是
检查了一个与用户目的无关、很容易稳定的输出。

固定网格的回归合同与自主网格任务也应分开。前者可以要求精确单元数量；后者应按照任务认可的精度、
约束和成本验收，不能因为合格方案的单元数不同就直接拒绝。

**有区分力的检查。** 在明确目标量和容差的候选任务中，让 Agent 说明初始离散化依据，并用额外的受控计算
检查目标量是否足够稳定。必须记录真正执行的模型、各轮结果和预算；只有口头提出细化方案不算完成。
多个网格之间的比较本身也不是普遍正确性的证明，必要时仍需独立参考或工程审查。

## C．模型实现与 API 正确性

### 4. 模型是否真的理解了几何、区域和修改范围？

**困难在哪里。** “找到了一个面”“集合非空”“section 已分配”“作业跑通”，只说明某些操作有结果。
用户真正关心的是：它是否是目标端面、目标实例和目标材料区域，约束与载荷的方向是否正确，修改后原有要求
是否仍成立。几何变化还可能使原先的索引、位置选择或集合成员发生变化。

**项目已有处理。** 项目已有从验证过的 seed 脚本出发的修改任务，分别检查孔洞拓扑、分区材料、加载方式等。
这比只看脚本差异更接近实际模型验收，但覆盖的是指定 seed 与合同，不是任意既有 `.cae` 模型的通用编辑能力。
[模型修改 suite][E3]、[项目约束][P0]

另外，ADR-0023 已有默认关闭的单表达式引用编辑合同：调用方冻结文件、原文、hash 和区间，写入前检查候选，
范围外文本受保护，存在未决写入或外部漂移时拒绝继续。它不是“完全没有编辑范围限制”，但也不能把它写成
通用工程意图验证：范围内的引用仍可能指向错误对象；该模式也不会运行 Abaqus 验证引用含义。
[ADR-0023][P7]、[编辑保护源码][P8]

**剩余困难。** 文件编辑权限、模型语义正确性和数值结果正确性需要分别检查。合法地只修改一个表达式，
仍可能选错集合；合法地生成新几何，也可能漏掉重建载荷区域。反过来，拓扑发生合理变化时，机械要求面数、
节点号或全部数组顺序不变，也会错误拒绝正确修改。

**有区分力的检查。** 对选定修改任务，检查“需求中的区域含义→修改后实际成员或几何位置→对应材料/边界/
载荷设置→本次输出”这一链条。候选错误包括选错端面、保留旧集合、改宽度时附带改材料。
这些是需要检验的错误注入场景，本文没有声称它们都在项目中发生过；详细设计见[原文核查的模型状态与错误注入部分][R1]。

### 7. API 理解不只包括方法名和参数，还包括对象与输出合同

**困难在哪里。** Abaqus 建模对象、装配对象、ODB 对象、vendor 容器和输出字段之间的关系，往往无法
只靠签名查询解决。某个对象可索引不代表可切片；某个字段可在 ODB 中读取，也不代表应当在输出请求中
以相同名称额外申请。这是“合法 API”与“完整工作流语义”的差别。

**项目的具体例子。** B31 梁弯曲 control 的三条轨迹，首次正式提取都误把 `RM3` 当成三分量 `RF` 字段中的
某个位置；诊断探针又都对不能切片的 `FieldValue` 序列做了切片。报告还记录了 vendor 值转 JSON 的问题。
control 最终通过，但分别用了 8、9、6 次 Abaqus 调用。

仅加“先正式脚本、读取分量标签、不要切片”等通用提醒后，三条仍重复字段归属错误，调用为 7、7、8。
后来在该任务中明确写端与读端合同、结果定义，并保留通用操作要求，`declared_odb_contract_v2` 的三条记录
都用了 3 次 Abaqus 调用，严格回放为 3/3。该报告中的写端要求是恰好 U/RF/SF，读端则区分 RF/RM、SF/SM
的 companion 字段；这是这个已核查的 B31/Abaqus 2024 合同，不是可不加条件推广到所有输出的规则。
[梁弯曲合同与收敛报告][E7]

**已经解决了什么，尚未解决什么。** 这说明项目能够通过轨迹定位可补充的接口知识与任务合同，
也说明失败不全是“模型不够聪明”。不过，v2 同时改变了可见合同和操作指导，每组仅三次，不能把改进归因到
某一句提示词，更不能据此宣布通用 API 理解已解决。

API Catalog、经核查的 runtime note、静态预检和真实运行证据各有职责。Catalog 能帮助绑定接口，
静态规则能拦截一部分已知错误；它们不能证明对象选对了、材料正确或数值结果满足用户需求。

**有区分力的检查。** 区分名称/签名错误、对象归属错误、容器行为错误、输出申请错误和结果读取错误。
进一步检查诊断脚本得到的有效结论，是否进入了实际交付脚本。探针单独成功，不等于正式任务已经采用了结论。

## D．错误诊断与修复收敛

### 8. 修复需要收敛，而且不能把任务改成更容易的问题

**困难在哪里。** 一次错误之后，Agent 可能反复试同类 API、增加诊断脚本、重新查相同证据，
消耗完预算仍没有进入求解。另一种候选风险是为消除错误或获得收敛，悄悄改变材料、载荷、界面或精度要求。
后者可能产出可运行结果，却不再回答原问题。

**项目已有证据和防护。** B31 v7 的指定 allowlist profile 为 2/3，通过轨迹分别使用
9/3/1 和 11/4/1 次模型请求/Abaqus/Solver；失败轨迹使用 31/12/0，仍未到 Solver。
三条均没有 policy denial。这能证明正常路径遵守指定运行范围，并暴露高成本失败长尾；
不能把成功率变化单因果归于 allowlist，也不能说限制文件名就解决了推理收敛。
[B31 allowlist 报告][E8]

项目已经有模型、运行、求解和 wall-clock 等预算，也有默认关闭的 typed-probe 结论与采用协议。
项目记录明确指出：某组 typed-probe 通过轨迹没有使用 probe，不能据此宣称 probe 带来收益。
增加预算与增加协议都是干预，不是自动成立的改进。[项目约束][P0]

**剩余困难。** 需要区分“下一次执行能排除一个新假设”与“重复没有新信息的试错”。
错误修复还应保留用户的物理合同；当需要改变该合同时，应形成可见的任务修改或澄清，而不是藏在代码补丁里。
这里提出的降载、替换连接方式或放宽精度等情形，是候选错误注入，不是本文认定已经发生的项目缺陷。

**有区分力的检查。** 对真实失败轨迹追踪：本次依据是什么、排除了什么假设、正式文件的哪个部分改变、
下一次运行验证什么。以模型/Abaqus/Solver 调用分布、预算耗尽位置和最终合同保持共同评价；
既观察能否省调用，也检查是否因提前停止而误拒本可完成的任务。

## E．执行与状态可靠性

### 10. 会话恢复、任务修改和外部 Job 恢复不是同一能力

**困难在哪里。** 中断后至少存在三份可能不同步的状态：模型记得做了什么，工作区实际留下了什么，
Abaqus 进程实际做到了哪里。仅恢复聊天记录，不能据此判断是否可以重新提交求解。
用户修改任务后，还要区分哪些旧事实可以继续利用，哪些旧结果已不能证明新要求。

**项目已有处理。** Harness/file-backed resume 保存历史、工具结果和累计预算；task revision 保留对话，
但重新确定工作区基线和 execution offset，旧物理验收不能穿透为新任务的成功证据。
未决三个 Abaqus 工具进入 `needs_reconcile`，在新的模型调用或重复运行前失败关闭。
损坏的 tool-effect ledger 也不能通过猜测重建运行安全性。
[ADR-0020][P11]、[ADR-0021][P12]、[恢复源码][P13]

**实际限制。** 目前没有据此完成 PID/Job 重新附着、人工 reconcile 后解锁或外部 Job exactly-once。
这不是“没有续跑”，而是“已有已完成步骤的会话续跑，未知在途副作用仍停止”。
历史 Windows 并行 JSONL 写损坏已有针对性修正，后续又移除了不安全的恢复 fallback；不应把这条历史问题
重新包装为未修复现状。[ADR-0021 的确认与边界][P12]

Provider 失败也会混入能力观察。单元选择两批的 3/6 包含基础设施超时；新批两个通过 run 均未使用 resume，
不能把通过归因于恢复机制。任务层成功数必须保留，模型行为分析则应另标基础设施不可判定项。[复测记录][E2]

**有区分力的检查。** 分别考察文件工具已经完成、CAE 已经完成、Solver 状态未决，以及旧任务完成后收到新 goal
四个切点。预期不应都是“自动继续”：有充分完成证据的步骤应复用，未知外部副作用应停止，新 revision 应重建
验收证据范围。这些检查不等于授权启动新的真实运行。

## F．独立验收、评测与能力边界

### 9. 最难扩展的部分之一，是独立验收，而不只是生成模型

**困难在哪里。** 对固定题可以预先定义隐藏 oracle；对开放工程任务，首先需要可靠的规格和真值来源。
若由同一 Agent 自行定义“什么算正确”并验收自己，错误前提就可能同时出现在建模与判断中。
让另一个模型重复检查，也不能天然产生独立物理证据。

**项目已有处理。** 普通 CLI 明确只接受执行证据；固定评测则由宿主独立读取 ODB，结合输入合同、
执行来源、状态和结果判断。二者职责分离是已有能力，不是待建设设想。
源码还表明，普通 verifier 检查的是 Agent 声明的交付物和已用阶段，不能穷尽自然语言目标应有的所有交付物，
也不能独立证明应该运行但实际上没有运行的某个分析已经完成。[ADR-0019][P3]、[执行验收源码][P4]

**验收器自己也会出问题。** 梁弯曲历史实验中，旧 verifier 只要求输出集合包含 U/RF/SF，
会放过合同不允许的额外 RM。改为该任务要求的精确集合后，一个 treatment 的历史 3/3 在严格回放下变成 1/3。
报告已保留修正与回放结果，不能继续把旧成绩当作当前合同的通过数，也不能把已经修复的宽松检查写成当前缺陷。
[梁弯曲验收修正][E7]

**剩余困难。** 验收需要回答：输入和区域是否对应当前任务；模型设置是否符合要求；是否完成请求的加载或时间范围；
结果是否来自本次正确 ODB 的正确区域、分量和帧；结果值是否符合独立标准。
要求也应在正确的地方可见：用户需要知道交付字段及其含义，模型不应看到隐藏真值和 oracle 内部实现。
固定案例中需要精确输出集合，不代表开放任务一律禁止额外输出。

**有区分力的检查。** 在固定任务验收器上加入错误输入与合理替代方案：前者检验误接收，后者检验误拒绝。
尤其要区分“脚本和 JSON 看起来正确”与“宿主从本次真实模型独立观测到了要求的状态”。
五层证据与候选错误注入在[既有原文核查第四节][R1]已有详细说明，这里不把它们写成产品已实现的通用 verifier。

### 11. 如何测出真正的能力，避免把环境或验收变化算成模型进步？

**困难在哪里。** 本项目一次结果受任务说明、Skill、模型与 Provider、检索内容、预算、工具协议和 verifier
共同影响。换了几项之后通过数增加，只能说明组合配置有新观察，未必能解释哪项产生贡献。

已有记录给出三个很具体的提醒：单元复测不能丢弃之前 1/3；梁弯曲改善包含输出合同的补全；查证协议失败
包含固定输出上限和 Provider 无效。它们分别对应选择性报告、合同不一致和失败归因问题。
[单元复测][E2]、[梁弯曲对照][E7]、[查证策略记录][E6]

**对当前项目有意义的测量。** 应在每个任务家族和配置内分别保留以下含义：

| 测量层 | 需要回答的问题 |
|---|---|
| 任务结果 | 全部启动中，多少完成约定任务；多少正确澄清或停止；多少未完成 |
| 可判定行为 | 基础设施正常交付任务时，模型具体在哪一阶段做错；无效项为何无法判定 |
| 工程证据 | 是否保持需求，模型状态与数值结果是否通过对应 scope 的独立检查 |
| 成本与稳定性 | 模型、Abaqus、Solver、wall time 和人工介入如何分布，长尾在哪里 |

按任务定义分别计分很重要：缺参数题的正确行为可以是澄清，完整仿真题却不能因为正确提问就算已经完成。
Provider 无效项可以从某项纯行为指标中单列，但必须保留总启动数和用户视角的任务结果，避免把环境成本抹掉。
同一简单板的参数变体与重复，不等于覆盖了多个独立建模能力。

**怎样定位瓶颈。** 可直接沿用[既有研究第五节的 A/B/C/D 设计][R1]：A 为同一受控执行环境下的基础条件，
B 加当前选定知识配置，C 提供人工匹配的正确证据，D 再提供工程师审定的建模步骤。
保持任务、模型、验收与可比预算，限制人工辅助不得泄漏隐藏结果。

C 比 B 好，提示知识选择或交付可能有问题；D 比 C 好，提示规划组合可能是限制；D 仍失败，则还要检查 API、
观测、执行、预算和基础设施，也要确认人工计划本身是否有效。这些差异是诊断线索，不是无混杂的唯一因果结论。
C/D 属于辅助条件，不应与自主 Agent 混成同一个排行榜，也不保证是能力上界。

**当前仍不能宣称的结论。** 少量固定任务的 2/3 或 3/3 是 smoke 证据，不能直接转为稳定工业成功率。
未预先匹配条件的追加尝试、增加预算和人工修订，应保留为不同证据阶段；验收器修正后的回放也要与原始成绩并列。
本次没有新增评测题执行或因果实验。

### 12. 支持范围和配置越来越多，维护难度也会进入主问题

**困难在哪里。** 同一 Coder 已经有知识入口、查证策略、运行范围、静态预检、编辑合同、交互策略和恢复状态等
多个可选行为。维护成本不只在模块数量，还在组合是否兼容、提示词与实际工具是否一致、历史报告对应哪版配置。

**项目已有处理。** strict request、显式 binding、launch、amendment、任务 revision 和独立的报告保留，
为这些边界提供了基础。当前合同也明确拒绝某些不兼容组合，例如纯编辑 scope 与 runtime static preflight。
因此不能仅凭目录多就判断架构混乱，也不应把默认关闭的试验能力描述成已获得产品收益。
[请求合同][P5]、[装配源码][P2]、[ADR-0021][P12]

**剩余风险。** 如果不断扩大任务类型，却没有同步增加可验证合同，最容易形成“开放入口很广，可信范围很窄”
的落差。若同时改 Provider、推理配置、提示词和评测规则，旧证据也很难解释新路径。
离线配置或 schema 对齐只能证明配置的接线，不等于真实模型遵循协议，更不等于完成新物理闭环。

当前三个受控运行工具限制 launcher、路径、预算和证据入口，但执行的仍是普通 Abaqus Python；
这不构成 OS 级隔离。若目标是本地可信用户工具，可以明确保留该边界；若以后转为共享计算或不可信用户服务，
外部 Job 所有权、资源隔离和恢复责任才会成为另一组需要独立设计、验证的要求。[项目约束][P0]

**有区分力的检查。** 对每个准备对外宣称支持的任务家族，能否指出：输入条件、允许自主决定的范围、
选用的 profile、实际交付物、验收 scope、失败出口和验证记录。答不出来的部分应保留为研究或能力边界，
而不是靠新增框架、数据库或更多 Agent 补足项目表述。

## 横向 K．知识缺口识别、查证与证据利用

### 5. Agent 能否发现自己需要知识，以及何时不需要查询？

**困难在哪里。** 同样是“不知道下一步”，可能来自本地名称未知、用户事实缺失、专业适用条件不清楚，
也可能来自 API 绑定错误。查询工具的存在并不能保证模型识别这些差别。

**项目已有处理。** 主动工具 `search_abaqus_docs` 接收问题与可选 `observed_context`，按已有索引信息组查询，
最多返回四条证据，并明确 `found` 不表示问题已回答。精确 API 有独立入口；报错后的自动提示和 Solver advisory
又分别受配置与证据条件约束，不能把它们混为同一种强制检索。[文档工具源码][P9]、[项目约束][P0]

六场景行为记录已经显示：模型会在本地证据充分时零查询，会在缺少用户材料输入时澄清，也会对另外三种
知识问题发起检索。与此同时，某个 API 修补虽然代码正确，解释却把针对单节点的 runtime note 扩展成了集合
的依据；一个诊断解释主要来自模型自身知识，检索并未返回所需章节。
因此，调用了检索、检索返回了内容、最终代码正确和结论受到证据支持，必须分别判断。[行为报告][E1]

**剩余困难。** 应当定位完整链条：是否意识到缺口；问题是否表达正确；语料是否覆盖；排序是否找到；
送达片段是否完整适用；模型是否把证据落实到正确动作。不能把所有失败都解释为“模型不主动调用 RAG”，
也不能把零查询本身当作失败。

**有区分力的检查。** 在同一个真实问题上分别检查工具调用前后的判断和正式脚本变化。
必要时采用已有研究中的人工匹配证据条件，观察正确证据直接送达后，错误是否仍存在。
这不需要新增分类 Agent；可以由评测侧对同一 Coder 的轨迹做标注。

### 6. 返回相关段落，与交付可以用于当前模型的证据，仍有距离

**困难在哪里。** 文档证据必须包含问题所需的条件、例外、对象范围和版本信息。相似的术语、页面标题
或“官方文档”标签，都不能自动证明片段适用于当前任务。

**已有具体观察。** 2026-09-05 的行为报告记录了以下问题：英文大写诊断中的普通词 `AT` 被识别成输出变量；
请求的 `OdbAssembly.nodeSets` 等成员访问没有得到充分覆盖；Standard 查询出现 Explicit 范围的片段；
解释超出了检索证据能支持的范围。文档语料记录为 Abaqus 2026 FD02，执行目标为 Abaqus 2024，
不能据此声称已证明跨版本 API 或具体行为兼容。[行为报告][E1]、[项目约束][P0]

context-v2 的后续回放进一步显示：所需的边界条件与精确时间输出章节实际上已在索引中，但没有进入返回的
Top-4；更长标题占用了原有 600 字符片段预算，使部分关键正文更早被截断。这说明“没答到”不一定是缺文档，
“元数据更丰富”也不一定等于实际交付的知识更多。该回放只有五条开发查询，无模型或 Abaqus 运行。
[context-v2 回放报告][E4]

**已有策略的边界。** sealed held-out 检索报告中，BM25、Dense、RRF 的 Complete Hit@5 分别为
23/30、24/30、25/30，RRF 相对 Dense 为 3 胜、25 平、2 负。净多一题是检索层观察，不能直接证明 Agent
任务更好，也不足以把混合检索视为必然更优的路线。[检索 held-out 报告][E5]、[ADR-0022][P10]

强制查证也有代价。`bounded_v1` 的八场景 batch-2 为 3 通过、4 模型行为失败、1 Provider 无效，
没有 Abaqus 调用、没有 live ranking 查询，仍未获得行为资格。问题包括跳过 assessment 后立即补查；
另有三例超过当次固定的 2400-token 输出限制。缺物理参数场景还受旧的首动作标准约束。
这些结果反映特定协议与实验配置的问题，不能外推为新 CLI 都有该输出上限，或先读文件永远是错误行为。
[查证策略 batch-2][E6]

**剩余困难与检查。** 应分别检查语料覆盖、符号提取、产品/版本范围、片段完整性、证据采用和协议成本。
对已有目标章节的失败，先追踪它在哪一层丢失；对于确实未覆盖的成员接口，再判断如何补源。
扩大 Top-K、增加文档、换融合算法或强制更多调用，都需要对应层的证据，而不能互相替代。

## 当前怎样排序这些困难

这里区分“已有证据值得优先分析”和“对最终目标重要但尚未充分测量”，不把所有条目排成开发待办。

**已有证据最具体的部分：第 5—8 点。** 文档误识别与证据范围、API 对象和输出合同、正式脚本的修复长尾，
已经能从本项目报告找到触发条件和代价。可以明确说这些机制曾经限制了任务表现，但仍要按版本区分已修正与未复测。

**最决定领域价值、也最需要补能力证据的部分：第 1—4 点和第 9 点。** 用户输入理解、专业选型、数值充分性、
实际模型语义与独立验收，决定系统是否能从“完成受约束脚本任务”推进到“可靠回答工程问题”。
当前不能仅靠 API 命中率、解释质量或固定 Gold 成绩跨过这层证据缺口。

**支撑结论可信的部分：第 10—12 点。** 多轮状态、Provider 与外部运行、评测归因和配置维护，
决定看到的成功能否复现、失败能否解释、任务修改后证据是否仍有效。已有基础应被保留，未实现的外部服务能力
则按真实部署目标讨论。

对现阶段最有解释力的问题是：在一个已限定的任务家族里，正确工程要求、匹配知识和工程师方案分别给定后，

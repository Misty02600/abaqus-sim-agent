# 专业能力与工业评测：科研 Agent 原文核查

核查日期：2026-09-13。

本文回答四个问题：专业知识不足如何补足；怎样证明理解了建模问题；如何解决 API 与实现问题；工业 Agent 怎样评测。内容区分“论文报告”“源码观察”和“本项目研究建议”。本轮没有运行第三方求解器或复现其成功率；研究建议不代表已经实现或形成正式架构决定。

## 一、原文具体提供了什么证据

### 1. ChatCFD：专业知识具体到文件依赖、边界条件和量纲

**论文报告。** 系统要求用户提供 `.msh` 或 `polyMesh`；其知识分成文件依赖、边界条件、物理量纲、求解器与教程模板等结构化部分。修复时检索相关参考文件，并结合当前配置和修改历史。物理一致性另行评估：解释器的 97.4% 保真度与整体 68.12% 的物理保真度不是同一指标，也不能直接视为同口径误差差值。受控求解器选择实验为 20/21，说明存在限定范围的自主选择，不能把它说成所有决定都由用户预先给定。[C1]（§§2.2–2.4、3.2、3.4）

**源码观察。** 固定提交 `2af6ca5d6f48657e5b1e09a588082fb8bb8e5790` 的 `case_run()` 以进程返回码判断运行成功；`main()` 据此返回 `Success`。这条运行链未包含独立物理结果比较，因此运行入口的成功标志不等于论文另行报告的物理一致性评价。[C2]、[C3]

`setup_cfl_control()` 会调整时间设置：稳态分支设置结束时间为 10；瞬态分支设置很小的时间步和 `endTime = dt * 10`。运行入口会在相应纠错条件下调用它。因此，用这条路径运行通过，不能直接证明完成了原任务所需的整个物理时间过程；还应核对最终时间设置及输出。[C2]、[C3]

外层纠错受 `max_running_test_round` 限制，但初始文件生成另有 `while not write_initial_files`，所读循环没有显式重试次数上限。预算审计应覆盖整条调用链，而不只检查求解重跑循环。[C3]

**参考价值判断。** 值得学习的是把专业约束落实到具体产物之间的关系，而不是只增加一段“你是 CFD 专家”的提示。对 Abaqus 可类比为：材料与分析步、单元与自由度、集合与载荷区域、输出请求与实际可提取结果之间的适配。这里是方法迁移建议，不表示上述兼容性检查已经存在。

### 2. ALL-FEM：微调能帮助实现专业要求，但验收与自治程度要单独看

**论文报告。** 工作把专家与教程代码、扩增后筛选的代码用于 FEniCS 微调，再结合执行反馈和建模分工。[A1]、[A2] Sample Problem 1 已指定平面应力和 `20 × 4` 网格；因此相关成功例主要验证正确落实题目要求。§3 的判分包含专家参考解叠图比较，以图尺度下无法区分作为通过条件，并非只判断可执行；但没有采用明确数值范数阈值。协调器无法可靠自行结束、需要人工终止循环，也是方法部分明确记录的限制。[A1]（§§2.4、3，PDF pp.12–13）

**数字口径。** v1 摘要把 71.79% 与多 Agent 关联，结果段将其用于两 Agent 微调组的 `28/39`；Figure 6 多 Agent 三类计数为 `15 + 13 + 2 = 30`，对应 `30/39 ≈ 76.92%`，正文也写多解决两题。本文保留这一版本内不一致，不擅自替作者确定最终口径。[A1]（PDF p.15）

**参考价值判断。** 微调路线值得参考，但需要先明确希望改善的是“解释物理”“遵循已给建模假设”还是“从工程描述选择假设”。它们应分别出题。把参考解比较从绘图升级为可复核数值检查、把终止条件交给宿主，都是本项目可研究的方向；不能用角色数量替代这两项保证。

### 3. MCP-SIM：“澄清”实际上允许推断缺失参数

**论文报告。** 该工作的 MCP 指 Memory-Coordinated Physics-Aware Simulation。论文在 12 个任务上报告 12/12，并把归一化方程残差低于 `10^-4` 和场分布合理性纳入评价。它不是只有执行检查；但残差收敛仍不同于与真实工程目标一致。[M1]（结果部分）

**补充材料证据。** Note 1 说明专家启发式进入提示模板；Figure 1 明确要求推断边界条件、估算材料参数；Figure 2 再把描述转成结构化字段。这里的 clarification 不能翻译成“遇到未知参数就询问用户”。[M2]（PDF pp.2–4）

**源码观察。** 固定提交 `e30e08c4ffee52a64a1ecc63d7b57d91b13130ef` 的 `InputClarifierAgent.clarify()` 调用模型后直接返回完整描述，失败则回退原输入；所读函数没有用户确认环节。`SimulationExecutorAgent.execute_simulation()` 检查进程异常及日志错误模式；该文件没有实现正文所述统一残差阈值和场分布判定。[M3]、[M4]

公开提交早于正式论文，所读执行器也不代表完整实验系统。因此合理结论是“发布源码与论文评测的对应关系仍需核实”，而不是认定作者完全没做物理检查。

**参考价值判断。** 把模糊任务变成有字段的建模描述有价值；但工程任务还需要记录字段来源。模型猜出的材料常数与用户测得的材料常数不能同等处理。一个错误材料模型也可能得到很小残差，因此自动补齐参数所增加的完成率，需要与需求忠实度一起报告。

### 4. 2D Frame：中间几何表示与专家规则有直接实验支持

**论文报告。** 系统在限定二维框架族内，把几何节点与连接关系表示为 JSON，再翻译为 OpenSeesPy；使用专家拓扑规则、完整代码模板和重复节点等检查。主实验为 20 个拓扑、各 10 次。§4.3 的三种框架消融保持规则与模板信息，分阶段组各为 10/10，合并几何与代码生成的组各为 0/10；合并组可执行但几何错误。这是比单纯“多 Agent 成功率更高”更有解释力的证据。[F1]（§§3–4、Table 2，PDF p.13）

**参考价值判断。** 可迁移的是把难以一眼验证的最终脚本，拆成能检查的中间产物；它不要求本项目立即增加 Agent。一个 Coder 也可先输出节点、区域、连接关系，再由工具检查后继续。论文没有覆盖任意三维几何、接触、材料选择与网格收敛，因此不能把这个受控拓扑结果当作通用 CAE 建模能力。

同样，重复节点规则需要物理语义。对接触面、界面模型或刻意分离的部件，几何重合不自动意味着应合并自由度；迁移规则时必须写明适用条件。

### 5. Generic Harness：必须控制知识输入，才能讨论架构贡献

**论文报告。** FoamBench 上，同一设置无教程、可选教程、强制教程分别为 `89/110`、`102/110`、`106/110`。但其通用基线本身包含教程对照、配置一致性和预处理顺序等工程提示。每配置单次实验，一些专业系统成绩引用既有论文，模型及条件不完全匹配。工具预算还包括网格生成，不能把“一次调用失败”解释为“首份求解代码错误”。[H1]（§§3–5、Tables 2–4、Appendix D）

**参考价值判断。** 这支持为本项目建立信息与预算匹配的强单 Agent 基线，不支持“领域系统没有价值”或“多 Agent 一定没用”。如果专业方案多拿到案例、规则和运行次数，最后的差异不能全部归给编排框架。

另外，各基准对成功的定义不同。进行横向比较前，应先确认检查的是进程、结果标量、完整场还是模型评分；不宜把论文表格里的一列成功率直接平均成“工业能力”。

### 6. FEM-Bench：把知识缺口与组合能力、测试能力拆开

**原文报告。** 本轮新增阅读 v2（2026-05-29）。基准包含 33 个计算力学代码任务，通过完整、部分、不给辅助函数区分知识与组合困难。实现需在容差内匹配参考输出；生成的测试需同时放行正确实现、拒绝指定错误实现。Appendix D 的有限提示优化实验显示，显著增益伴随具体领域知识进入提示；不能概括为通用“认真思考”指令有效。该实验只针对受控任务，且相关子问题参与优化。[B1]（§§3.6、4.3、Appendix D，PDF p.37）

**参考价值判断。** 对本项目最有用的是“评测验收器本身”：一个检查脚本即使每次运行成功，也可能把错误模型全部放过。应给它正确算例和人为植入的错误变体，观察是否能区分。FEM-Bench 测的是计算力学函数，不是完整 Abaqus Agent；迁移的是验证方法，而不是直接采用其分数。

## 二、专业知识不足，具体应该分成哪几种问题

以下是根据上述证据形成的本项目研究建议，而不是对某篇论文的复述，也不是实施计划。

### 1. 用户事实未知：检索通常不能替用户决定

例如材料牌号、实测本构、界面参数、真实载荷方向和装夹条件没有给出。文档能解释参数是什么，却不能告诉系统这次试样的真实值。

建议把输入字段至少区分为“用户给定”“现有文件读取”“根据已知量推导”“任务允许的默认假设”“仍缺失”。推导值保留推导关系；默认假设保留适用条件；缺失但决定物理问题的字段进入 `needs_input`。演示任务可以明确授权典型材料或归一化参数，但应在结果中保留该假设。

不能因为某篇论文允许估算材料，就把“自动填满 JSON”作为工程成功。字段完整与事实正确是两回事。

### 2. 专业概念未知：需要适用条件，不只是定义

“平面应力是什么”与“这次能否用平面应力”需要不同证据。后一问题需要联系实际几何、约束、载荷和目标量。单独返回一段术语定义，不足以完成选择。

建议领域检索返回一个可用的判断单元：适用条件、反例或限制、所需输入、会影响的建模决定，以及后续验证方式。例如，某种降维近似能满足整体位移目标，不代表也能给出局部厚度方向应力。知识条目应帮助模型判断何时不能照搬相似案例。

这种表示不要求另建分类 Agent，也不要求对 Abaqus 全部 API 做强类型封装。主 Coder 可以按需查文档；真正需要稳定保留的是判断依据及适用边界。

### 3. 知道候选方法但不知道当前精度：需要计算验证

“初始网格取多少”与“网格已经足够细”应分开。初始密度可来自案例、经验或默认策略；充分性必须联系目标量验证。

建议任务先声明关注量 `Q`，例如端点位移、反力、路径平均应变或某区域积分量，再进行逐级加密。一个示意指标为：

`delta_Q = abs(Q_fine - Q_coarse) / max(abs(Q_fine), Q_scale)`。

`Q_scale` 用于避免接近零时相对误差失真，应在题目或验收规范中固定。至少观察连续加密的变化趋势，不能让模型只跑两张随意选择的网格，见到差异小就宣布网格无关。网格序列、单元族、几何近似和目标量也应可追溯。

这只是候选评测方法。误差容限必须结合具体任务预先确定；小的相邻网格差异也不构成对连续真解误差的普遍保证。

### 4. API 不熟悉：把合法调用与建模语义分开检查

API 查询回答方法归属、参数、枚举、对象类型、版本和必要调用顺序。领域文档回答为什么选择该模型、限制是什么、哪些输入还缺失。

例如：模型已经正确决定采用某种二维假设，却调用了不存在的方法，这是 API 问题；API 完全合法，但把另一种物理假设实现进去，则是建模或语义实现问题。两者都能表现为“代码错误”，但只有前者能主要依赖参数卡解决。

建议保留两条可独立观测的链：

`需求与物理条件 → 建模选择及依据 → 实际模型属性`；

`目标对象与操作 → 版本匹配的 API → 调用及执行证据`。

报错后的自动证据增强仍有必要：模型在错误发生前不一定知道自己缺知识。对于未报错但物理不对的情况，则需要独立检查模型与结果，不能等求解器替用户发现需求被误解。

## 三、如何证明模型真的理解建模问题

不建议把自述“我理解了”或一篇流畅报告作为主要证据。建议给同一物理问题设计成对任务，观察因果变化，而不只积累更多参数变体。

| 对照任务 | 固定什么、改变什么 | 可以定位的能力 |
|---|---|---|
| 给定建模方案 / 只给工程描述 | 物理问题与目标量相同；移除单元或简化假设提示 | 区分执行方案与选择方案 |
| 完整参考实现 / 只给 API 文档 | 求解目标相同；降低现成实现支持 | 区分模板改写与知识应用 |
| 完整物理输入 / 缺一个关键参数 | 只移除真实材料或边界条件信息 | 检查是否识别信息不足并正确询问 |
| 原工况 / 改变一个关键假设 | 改变约束、变形范围或目标量之一 | 检查是否相应修改模型，而非复用旧方案 |
| 给定网格 / 自主满足精度要求 | 目标量相同；取消固定网格 | 区分划网格与验证离散误差 |
| 正确模型 / 可运行的错误模型 | 植入单位、区域、方向或材料错误 | 检查是否识别不报错的物理错误 |

第一类对照必须避免“去掉必要信息”导致题目本来就不唯一。只给工程描述时，仍要给出足够确定物理问题的事实；否则正确行为可能是询问，而不是强行选一个单元。

评价单元选择也不应只比较一个指定字符串。可以有多种合理离散：只要满足前提、目标量与精度要求，允许不同单元族或网格策略。题目可设置“允许的方案与约束”，而不是把专家参考脚本的每个细节都当唯一答案。

为检测是否只记住模板，留出应优先按物理问题族、几何族或建模机制划分。将同一教程的尺寸和载荷随机改数后分到训练与测试，只能提供较窄的泛化证据。应同时报告原型数量与参数变体数量。

## 四、工业 Agent 评测应保留五层证据

下面是一套适合本项目讨论的验收分层。它不代表论文已有统一标准，也不意味着当前 CLI 已实现全部检查。

| 层次 | 核心问题 | 验收证据举例 | 不能替代什么 |
|---|---|---|---|
| 需求忠实度 | 是否在解决用户原来的问题 | 单位、材料来源、边界、目标量、已确认假设 | 不能靠运行成功证明 |
| 模型语义与实现 | 正确选择是否真的写进模型 | 实际单元、截面/材料赋值、区域、自由度、分析步、输出请求 | 不能只查函数签名或生成前说明 |
| 执行与数值求解 | 是否完成规定求解 | 退出状态、终止时间、求解状态、必要输出、收敛诊断 | 不能证明物理问题正确 |
| 结果正确性 | 目标量是否可靠 | 解析解、独立参考解、守恒/平衡、精度与敏感性检查 | 单个标量吻合不保证所有场都对 |
| 任务级可靠性 | 能否稳定、有限成本地完成 | 重复成功率、误接受、预算、人工介入、失败原因、多轮变更一致性 | 单次成功不能证明稳定可用 |

应把“运行通过但物理错误”单列出来。它比明显报错更值得关注，因为用户更容易据此作决定。至少同时记录：运行成功率、严格任务通过率、物理错误被错误接受的比例。各指标分母写清楚，不混合“全部任务”和“已可运行任务”。

参考解也要有身份。解析结果、独立网格收敛解、实验结果、作者人工判断，证据强度和适用范围不同。对于实验数据，还要考虑输入不确定性；不能把未知材料参数导致的差异归为 Agent API 失败。

### 工程意图保持与模型状态核查

五层证据需要通过同一项工程要求连接起来。例如，“只修改导线宽度”既规定了本次应改变什么，也约束了哪些材料、载荷和界面设置应保持。只检查新脚本能运行，无法判断这种要求是否被贯彻。以下是一种候选研究方法，不是当前产品新增的必填中间格式或通用验收门禁。

**先记录需要保持的工程含义。** 一份紧凑的建模说明可以记录分析目标、单位约定、参数来源、物理假设、关键区域、载荷与约束、界面或接触行为、目标输出，以及本次修改允许改变和必须保持的条件。这里记录的是与验收相关的决定，不要求枚举所有 Abaqus 对象。材料常数等必需事实仍遵守第二节的来源与澄清规则；文档中的典型值不能替代本次试样数据。

**再把每项声明映射到实际模型事实。** Agent 写出的说明只是待核查的主张。应从对应任务版本的 CAE/INP 读取设置，再结合本次求解日志和 ODB 检查实际完成情况；不能只重读生成脚本中的注释或 Agent 自报的 JSON。

| 工程要求 | 候选核查事实 | 容易产生的误判 |
|---|---|---|
| 参数与单位一致 | 任务中的单位约定、参数来源与推导关系，实际几何、材料和载荷数值 | 不能假定模型文件自带完整单位语义，也不能仅凭数值看似合理就通过 |
| 材料和截面赋给正确部件 | 实际材料/截面定义、赋值区域、所属实例、覆盖范围与遗漏 | 定义了正确材料，不代表目标区域实际采用了它 |
| 载荷和约束作用于指定位置 | 集合的真实成员、位置与范围、实例归属、自由度，以及适用时的方向和坐标系 | 集合非空或选择调用成功，不代表选中了工程描述中的边界 |
| 界面行为符合任务 | 接触或界面属性、配对表面、所属实例、相邻关系，以及适用时的表面侧别与方向 | 表面名称正确，不代表配对关系或相互作用性质正确 |
| 离散与求解条件合适 | 实际单元、局部网格、分析步和数值控制，结合任务目标检查精度 | 配置存在或求解器收敛，不代表满足目标量的精度要求 |
| 输出对应目标问题 | 输出请求、区域、分量、坐标系；本次 ODB 中的可用帧和实际提取值 | 请求了某个变量，不代表取得了正确位置、分量和工况下的结果 |

区域映射尤其需要随几何变更重新核查。改变尺寸、分区或构造顺序后，原来的面索引、坐标选择或集合成员是否仍对应“左夹持端”“导线与基底接触面”，必须由任务相关的几何与语义条件判断。不能普遍锁死面编号或面数量：合法分区可能改变实体数量。应优先检查位置、范围、归属、覆盖和适用时的方向等性质；可视化可辅助发现选错区域，但不能替代对象与结果证据。

可保留的最小追溯关系是：

`工程要求及来源 → 预期设置 → 实际模型/本次运行观察 → 通过、失败或尚未核实`。

每条观察还应绑定任务修订、模型或输入文件版本和运行标识。没有读取到相关属性应记为“尚未核实”，不能因为没有发现异常就按通过处理。具体以表格、日志还是已有评测记录承载，可以另行验证；这里不要求产品改用固定模型描述语言或确定性渲染器。

**修复也要保持工程意图。** 修正不存在的 API、对象引用或拼写，与改变材料本构、载荷、界面行为或非线性假设，是不同性质的修改。即便只是调整增量、收敛控制或网格，也需要检查其对数值精度与完成条件的影响。自动修复应核对实际变更及其依据，再复查受影响的要求；不能把“报错消失”作为唯一目标。用户明确修订任务时，以最新要求为准，而不是永久冻结初始设置。

以金属导线/Ecoflex 基底拉伸并提取界面附近应变为例，尺寸、材料参数、目标拉伸和界面参数应来自用户或已有可信文件，缺失时询问。假设任务已明确要求某种可滑移或可损伤的界面行为，那么把它改成 tie、减小目标加载量或替换材料常数，即使有助于运行，也改变了原问题。只改导线宽度的任务，还应检查材料、边界、界面和目标输出是否保持。这个例子用于说明核查方法，不声称当前项目已经支持这类非线性模型的完整验收。

### 一个可以说明分层作用的例子

设一个均匀直杆在小变形线弹性轴向受力，题目完整给定 `F、L、E、A` 及端部条件。由应力 `F/A`、应变 `F/(EA)` 得端部伸长 `u = FL/(EA)`。

若 API 调用完全正确，但把力施加到错误集合，运行层可能通过，模型语义层和结果层应失败。若使用错误单位同时又碰巧在输出换算中抵消，某一个位移可能接近参考值，但模型输入检查和第二工况应揭露问题。若只让模型自己计算公式并把数值写入 JSON，则还没有验证实际 ODB 结果。

因此验收器应从本次求解产物独立提取值，并核对工况、模型与运行标识；不能把 Agent 自报的数值当求解事实。直杆例适合验证这条链，但不能证明接触、超弹性或界面损伤能力。

### 验收器本身也要接受错误注入测试

错误注入应围绕要识别的工程失真设计，并为每个错误变体保留正确对照。下面是候选故障与回归场景，不是本轮观察到的仓库缺陷，也不是已新增的测试；现有固定 Case 是否覆盖某一窄场景，应以各自验收合同为准。

| 场景 | 人为构造的错误 | 期望检查 |
|---|---|---|
| 只修改导线宽度 | 宽度正确，但材料、边界条件或界面属性被一并改动 | 几何变更符合要求，同时拒绝未授权的物理设置变化 |
| 改变几何或构造顺序 | 原选择表达式仍返回非空集合，却指向另一位置或实例 | 重新核对区域的工程含义；合法分区造成的成员数量变化不能自动判错 |
| 修复求解失败 | 将明确要求的界面行为替换为 tie，或偷偷降低目标加载 | 拒绝改变原工况来换取运行成功；合法数值调整仍需完成目标并满足精度要求 |
| 只完成部分加载或物理时间 | 仅留下中间帧，或修改结束设置后声称完成原目标 | 同时核对请求条件、实际步与加载历史、终止位置和可用结果，不能仅看最后一个现存帧 |
| 新运行失败后沿用旧结果 | 新任务没有有效结果，却读取上一次 ODB 或 results.json | 结合任务修订、当前输入、运行记录与产物身份拒绝错配，不能只检查文件存在 |
| API 合法但语义错误 | 材料赋到另一部件、选错表面或方向、提取另一输出分量 | 在模型语义与结果层拒绝；允许执行层本身显示运行成功 |
| 零载荷或单位错误 | 删除载荷得到零解，或把材料、几何、载荷换算错 | 联合检查输入、载荷存在性和独立响应，避免单一平衡检查或偶然抵消放过错误 |

一个合格的验收器应放行正确参考算例，并拒绝预先声明应识别的错误变体。也应加入满足物理条件的合法替代方案，检查是否因集合编号、脚本写法或非关键网格差异而误拒绝。对于无载荷零解，需要结合任务要求的载荷存在性或非零响应，不能只靠守恒检查。

结果应分别记录错误变体被误接受的数量、正确对照被误拒绝的数量、对应分母和失败层次。只覆盖这些注入场景的结果，不能外推为生产任务中的整体误接受率；检查数量多也不等于有辨别力。

## 五、怎样设计对本项目有解释力的实验

### 1. 先匹配条件，再比较系统形态

建议固定底座模型、版本、推理设置、题目、求解器、可读资料、预算和验收器，再单独改变一个因素。研究单/多 Agent 时保留相同知识；研究检索策略时保留相同执行与修复机会；研究微调时区分微调本身与更长运行预算的贡献。

“无额外知识工具”“仅 API 查询”“增加可选领域检索”“强制提供已匹配领域资料”“增加报错自动证据”可以形成不同实验条件，但不宜同时改变多个因素后只报告一个总增益。恰当资料由人工匹配时，测试的是获得帮助后的表现，不代表系统已经学会何时检索、检索什么，也不构成数学上保证的能力上界。

检索调用率也不是质量指标。应统计：缺知识任务中是否获得合适证据、检索是否改变了错误决定、资料无关时是否造成误导、知识确实不足时是否能停止并询问。

### 2. 瓶颈定位对照实验：A/B/C/D

这一候选实验回答一个具体问题：任务失败主要发生在获得所需知识、把知识转成建模方案，还是落实方案并检查实际模型的过程中？四组用于诊断，尚未运行，不是新实施计划，也不预设必须增加 RAG、微调或多 Agent。

**共同条件。** 使用同一批任务、同一模型及版本与推理设置、相同初始工作区、求解器、执行工具、修复机会和独立验收规则。请求与运行预算设置为可比，记录实际消耗。各组都保留必需的权限与执行边界，以及普通运行结果和原始报错；不能为构造通用基线而给 A 开通产品没有的通用 Shell，或去掉必要保护。这里仍使用 `run_cae_script`、`run_solver_job`、`run_abaqus_python` 三个受控运行工具。基础提示中不可拆分的领域说明也要登记，不能把 A 描述成完全没有领域信息。

| 条件 | 相对前一组增加什么 | 主要观察目的 |
|---|---|---|
| A：通用基线 | 任务、工作区、受控执行工具及必需说明、普通执行反馈、固定预算；不附加本实验指定的专门知识支持 | 获得不增加领域知识支持时的参照表现 |
| B：现有领域增强 | 在 A 上启用明确选定的 API 查询、文档检索或报错证据配置 | 判断这个具体领域增强组合是否改善任务表现 |
| C：人工匹配的恰当证据 | 在 B 上提供人工为当前问题匹配的文档片段、API 说明和必要上下文 | 观察证据确实送达后是否仍会失败 |
| D：明确建模方案 | 在 C 上提供工程师给出的建模假设选择与关键实施步骤，由 Agent 完成实现 | 观察给定方案后的执行能力，而非自主选择方案的能力 |

B 必须冻结具体 profile、资料版本、开关和预算，而不是笼统写“启用本项目所有功能”。API Catalog、文档检索、Solver diagnostic advisory 等有独立启用条件；实验中实际开启哪些，就按配置和轨迹记录哪些。A/B 同时增加多项支持时，只能讨论这个组合的贡献，不能把差异全部归因于检索算法。

C 的人工资料应有来源与适用条件，并在任务执行前固定准备规则；不能依据某次输出事后挑选最有利片段。它不提供最终参考脚本、隐藏目标结果或验收器内部信息。D 进一步给出建模决定和步骤，但仍由 Agent 编写与执行脚本；工程师方案自身也需经独立审查确认可行，不能把错误方案导致的失败直接归给 Agent。任务公开的目标与精度要求在各组保持相同，隐藏答案和验收器内部阈值不泄露。

这里额外提供的是知识或方案，不是缺失的用户事实。如果真实材料参数、界面条件或目标加载尚未确定，C/D 仍应进入澄清流程；人工证据不能替用户编造这些输入。

**怎样解释组间差异。** 应比较同题的严格通过与失败层次，而不只是工具调用数或运行通过率。

| 观察 | 可以形成的诊断线索 | 仍需排除或继续区分的原因 |
|---|---|---|
| C 优于 B | 知识送达环节值得重点检查 | 可能是未触发查询、查询表达、检索覆盖、排序、截断或呈现方式；不能直接断言 retriever 有问题 |
| D 优于 C | 从证据到建模方案的转换可能存在缺口 | 还要检查证据本身是否可理解、约束是否完整，以及人工方案是否额外缩小了任务范围；不能推出普遍缺乏专业推理能力 |
| D 仍失败 | 给定方案也不足以完成任务 | 区分 API/对象操作、区域与状态核查、执行反馈、预算或 Provider/环境故障；基础设施故障独立标记 |
| 运行成功但严格验收失败 | 运行通过率掩盖了需求、模型或结果错误 | 应按第四节检查具体失真，不能仅通过增加重跑次数来优化可运行率 |

例如 C 比 B 改善后，应查看相关证据是否被查询、返回、完整呈现并正确采用，再做只改变某一个环节的消融。D 比 C 改善，则可继续区分建模假设、单元/离散选择、区域组织与实施顺序等子问题。组间差异本身只是定位入口，不是唯一因果解释。

C/D 增加了人工匹配或规划，不能作为与自主系统信息条件相同的榜单竞争者。记录人工准备时间、送入的资料与方案规模、模型输入和运行成本；额外帮助也可能增加上下文负担或引入误导，因此成绩不保证按 A、B、C、D 单调上升。

**样本与报告。** 同题重复运行，尽可能交错安排实验条件，保存逐题结果、失败分类、人工介入和成本。基础设施失败应单列，同时保留发起总数、有效运行数与严格通过数，避免只删掉失败再计算成功率。预算与小样本不确定性的报告遵循下一小节。历史失败案例适合发现机制，但它们不是生产分布；形成假设后，应另用独立留出的代表性任务确认，不能用同一批被反复调试的失败题宣称泛化提升。

### 3. 预算应覆盖真正昂贵的环节

分别记录模型调用、工具调用、求解次数、求解计算成本、等待时间及人工介入。网格生成、初次求解和错误后的重跑不要混记为同一种“反思轮数”。

建议同时报告固定预算内的首次严格通过率、允许重试后的通过率，以及各题重复试验结果。一次最好成绩不能替代稳定性；多个同源参数变体也不能当作同等数量的独立工程问题。

样本小时保留原始计数和逐题差异，避免只报百分数。进一步比较置信区间时，应考虑题目家族相关性；不能把同一原型的大量变体当完全独立样本制造虚假的精确性。

### 4. 多轮任务应检查状态，而不只是最后一句回答

用户把载荷从力改成位移、要求改变精度、补充材料数据、指定新的目标量时，需要核对最终模型是否对应最新要求。旧工况的结果文件不应被接受为新任务答案。

可以设计：第一轮信息不足并正确询问；第二轮补全输入后建模；第三轮更改载荷；第四轮要求比较两种网格。验收分别检查问题澄清、变更传播、产物归属和数值比较，最后再给整体通过结果。

对于预算耗尽、文档没有所需知识、求解失败等终点，应预先规定合适状态。让模型或人工无限循环到某次成功，会改变任务难度，也掩盖失败率。

## 六、对本项目的具体取舍建议

当前最值得沉淀的不是新的角色名称，而是三类可检查产物：建模决定及其来源、实际模型中的语义属性、独立数值验收结果。它们能接在已有 Coder、执行工具和宿主验收边界上，不需要因本轮调研立即更换框架。

知识侧应分别服务“选择”和“实现”。前者提供适用条件与验证办法，后者提供版本匹配的 API 与对象约束。错误反馈侧保留自动证据；结果侧把需求与物理错误从代码异常中分离。首先用成对题判断真正的瓶颈，再决定是扩充文档、结构化规则、微调还是拆分流程。

本轮证据不足以证明任一所读项目已解决通用的自主单元选择、网格充分性判断和任意材料建模；但它们分别提供了可复用的方法和可检验的局部实验。论文、开源代码、实验可复现性、工程覆盖范围应分开评价。没有完整产品不等于没有参考价值，有论文也不自动意味着达到工业交付条件。

## 仍需保留的不确定性

ALL-FEM 的摘要与 Figure 6 口径尚未通过期刊全文或作者更正解决。MCP-SIM 的论文评价与所读公开执行器不是同一层证据，未定位完整对应的残差验收实现。2D Frame 尚未确认可用于完整复现的源码仓库。本轮没有生成或运行任何上述项目的仿真结果，因此不把论文成功率写作本地验证成绩。

附加讨论中出处缺失的商业产品进展、发布日期和 FEABench 数字没有纳入已核查证据；不能借用名称相近的 FEM-Bench 来源补足。本次增加的工程意图核查、故障场景和 A/B/C/D 对照仍是研究建议，尚未据此新增产品检查或运行实验。

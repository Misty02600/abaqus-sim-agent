# AbaqusAgent：完整案例、建模约束、修复闭环与评测边界

核验日期：2026-09-13。返回[调研索引](README.md)；书目见[相关论文与阅读记录](相关论文与阅读记录.md)。

## 阅读结论与证据范围

**AbaqusAgent 最值得本项目研究的是“完整参考案例如何帮助构造一个可求解模型”，以及运行反馈如何支持修复。**
它的主要生成目标是 Abaqus `.inp`，与本项目通过 CAE Python 创建模型的路线不同。因此，它提供了补充
建模上下文的思路，但不能被当作 Abaqus Python API 可靠性已经解决的证据。[P1][C1][C4]

本文区分四种材料：**论文报告**是作者实验与方法描述；**源码观察**来自固定提交的静态检查；
**分析**是根据这些材料作出的判断；**迁移建议**仅为待验证的适用方向。尤其不能把论文中的专家结果评审
写成开源工作流已经自动执行的物理验收，也不能因为源码未发现独立 oracle，就说论文完全没有验证物理结果。

## 1. 它试图补足哪几类不足

论文面对的问题不只是关键词写错，还包括边界条件、载荷、输出和离散模型定义不当。[P1，§1–2]
从实际实现看，可以把其应对方式分成以下四类。这是本笔记的分析框架，而非论文额外提出的分类器。

| 不足 | 实现提供的信息或反馈 | 仍需保留的边界 |
|---|---|---|
| 需求没有说清 | Interpreter 检查几何、材料、边界条件、载荷、输出五类信息 | 五类字段齐全不等于所有物理假设充分，也不保证判断正确 |
| 不知道怎样组织模型 | 检索完整案例的问题说明与输入文件，提供节点、单元、集合、材料、步骤等组合实例 | 相似案例不自动具有相同的物理适用性 |
| 不熟悉 INP 语法与常见组织方式 | 示例模板及 Input Writer 的专家提示 | 提示中的工程约束不等于通用 Abaqus 语法要求 |
| 首次生成无法运行 | 读取求解错误，Reviewer 分析，Input Writer 重写并重跑 | 没有错误日志不能推出建模符合需求或结果正确 |

**分析：**完整案例的价值在于展示多个定义如何相互配合。单个 API 条目可能说明如何创建一个集合，
却不能独自说明目标边界应选哪些实体、为何采用这种约束、输出怎样对应所求物理量。案例提供这种上下文，
但把案例迁移到新问题仍然要求模型判断哪些结构能保留、哪些物理定义必须改变。

## 2. 主链路与“六个 Agent”的实际含义

论文的六个角色是 Interpreter、Architect、Input Writer、Runner、Reviewer 和 Visualization。
固定源码通过 LangGraph 注册相应节点，主要路径如下。[P1，§2.1][C1][C2]

```text
用户需求
  → Interpreter：检查与改写
      ├─ 必需信息缺失 → 返回缺失项并结束本次图执行
      └─ 继续
          → Architect：描述任务并检索一个案例
          → Input Writer：生成 AbaqusInput.inp
          → Runner：执行并解析错误
              ├─ 有错误且预算允许 → Reviewer → Input Writer 重写 → Runner
              ├─ 无已识别错误且 ODB 存在 → Visualization → 结束
              └─ 其他终止分支 → 结束
```

**源码观察：**生成器直接组织节点、单元、集合、材料和分析步等 INP 内容。主图中的 meshing/HPC 节点没有
作为当前有效节点注册，部分注释保留 OpenFOAM 名称，不能据此认定这些能力正在运行。[C1][C4]

Runner 是外部执行包装；当前可视化节点启动固定的 Python 脚本，并未在该节点看到新的 LLM 生成过程。
因此，“六个角色”不应直接解释成六个自主工具循环或六套不同模型。角色划分、图节点划分和独立 Agent
数量应分别判断。[C7][C9]

**输入边界：**Interpreter 的提示明确要求保留用户技术细节、不补造数值，并报告缺失项。不过，
`route_after_interpreter()` 的缺失分支会结束图执行。这是缺失信息检测与停止的证据，不能单凭它宣称
已经实现保存会话、接收补充输入并原地续跑的多轮澄清系统。[C2]

## 3. 案例知识库到底存什么，怎样检索

### 3.1 检索单位是完整案例

论文报告 104 个案例，其中 71 个来自 Abaqus benchmark manual，33 个由作者整理为教材式问题。
每个案例包含任务元数据、物理问题描述和完整 INP。[P1，§2.2]

源码的建库脚本以 `<case_begin> ... </case_end>` 为记录边界，每个记录构造一个 Document，
保留全文在 `full_content` 元数据中。没有在这条建库路径中看到按固定长度拆分为普通文档片段的步骤。
向量模型为 `text-embedding-3-small`，索引使用 FAISS。[C3]

**分析：**这类材料更接近“怎样把一个问题完整地建出来”的范例。它与本项目的官方文档片段检索和精确
API Catalog 有不同职责；三者之间不宜只用一个“RAG”标签抹平差别。案例还需要记录有效条件，
否则全文越完整，模型可误继承的尺寸、载荷和约束也越多。

### 3.2 当前源码的检索过程

Architect 先将需求表示为 `case_name`、`case_domain`、`case_category` 和 `case_material`，
分类提示参考知识库已有取值。随后检索 15 个向量候选，优先保留 domain 规范化后精确相等的记录；
没有这样的记录时，回退到全部候选。最后按下式重排，只返回第一名的完整内容。[C5][C6]

```text
priority = 0.60 × name_similarity
         + 0.30 × category_similarity
         + 0.10 × material_similarity
```

字段完全相同时记为 1；否则组合词集合交并比与 `SequenceMatcher`：
`0.6 × token_overlap + 0.4 × sequence_similarity`，name 的部分匹配上限为 0.80，
category/material 为 0.70。[C5]

这里所谓 hybrid 是**向量召回、元数据筛选和启发式字段重排**的组合；该路径没有 BM25 或 RRF。
不能据此认为本项目已有的 BM25/Dense/RRF 实验得到了外部验证。

### 3.3 需要保留的复现细节

| 观察 | 对理解方法的影响 |
|---|---|
| 论文 §2.1 写 name/category/material 为 30/60/10；Algorithm 1、§2.2 和固定源码为 60/30/10 | 存在论文内部表述差异；本文按源码解释实现，复现实验需明确采用哪组权重 |
| domain 无匹配时回退全部候选 | 这是优先筛选策略，不是始终保证物理领域一致的硬约束 |
| 当前选择路径未见相关性拒绝阈值 | “第一名”不能解释成“有足够证据支持目标问题” |
| 重排器把 `score` 作为 FAISS 同分决胜项，但当前 `retrieve_faiss()` 不返回这个键 | 当前所有候选在该项上使用默认值；不能声称数值距离决胜已经有效接通 |
| `file_dependency_threshold=3000` 对选中全文计数换行符 | 它不是 token 上限，也不是输入窗口大小 |

这些是方法复现与源码解释上的差异，并非本轮运行所得的错误率。[P1，§2.1–2.2][C5][C6][C10]

**迁移分析：**最有价值的部分可能是“用元数据帮助找到完整建模上下文”，而不是这组固定权重。
本项目若引入案例，仍需区分检索相关性、建模适用性和用户参数来源；一个金属板案例命中，并不能替用户
决定厚度、是否考虑大变形或材料本构。

## 4. Writer 怎样使用领域知识，Reviewer 怎样修复

### 4.1 案例用作参考，用户需求决定物理任务

初次生成提示要求先阅读案例的问题描述和 INP，识别几何、网格、集合、材料、步骤与输出组织方式；
随后根据用户的物理意图修改。提示明确把用户需求放在参考案例之前，不允许盲目继承载荷、约束、
单元选择和分析步。[C4]

这条原则值得保留，但它仍然是交给 LLM 执行的提示。要判断实际遵守情况，需要检查生成模型：
例如用户要求弯曲时，不能因为模板能运行就接受仍然施加轴向压缩的输入文件。

初始提示还鼓励规则网格使用 `*NGEN`、`*NFILL`、`*ELGEN` 等生成式表示。
**分析：**对于确实满足前提的网格，这可以缩短节点、单元的显式枚举；它没有消除拓扑设计问题，
也不证明任意带孔、接触或复杂三维几何都能可靠离散。

### 4.2 提示中的硬规则存在适用边界和内部差异

| 规则 | 初次生成提示 | 修复提示 |
|---|---|---|
| 最少单元数 | 20 | 10 |
| History output | 除非用户明确要求，否则不包含 | 提示直接禁止 |
| Element output | 要求全局输出，不带 ELSET 限定 | 同类限制 |
| 文件组织 | 规定关键词顺序、section 放置和 BC/load/output 放置 | 继续规定类似顺序与放置方式 |

这些是当前实现自己的生成策略，不应抄写成“所有 Abaqus 模型都必须如此”的规则。
尤其初始与修复阶段的要求不一致，会使同一个任务在错误修复后受到不同约束；这是静态提示差异，
本轮没有测量它实际造成多少失败。[C4][C8]

对本项目而言，案例或 Skill 中的规则应说明适用对象和来源。参数完整性、单位一致性、用户约束保持等
检查可以持续存在；固定单元数量或输出选择则应由任务与验收合同决定，不能因为参考项目这样写就全局采用。

### 4.3 修复依赖哪些上下文

Reviewer 接收当前文件、选中的案例、错误日志、用户需求及历史错误/建议，生成原因分析、最小修改建议和
检查项；实际文件重写由 Input Writer 执行。重写返回完整文件内容，而不只是结构化语义补丁。[C8]

这有助于避免每次修复都遗忘原问题，也提供了识别重复错误的上下文。但提示中的“不要改变物理问题”
不构成外部保证；建议改用其他分析程序或简化模型时，尤其需要重新检查是否仍在解原任务。

论文把修复上限描述为 15 次迭代。固定源码中 Runner 和 Reviewer 都增加同一个 `loop_count`，
所以 `max_loop=15` 不能直接换算为 15 次求解或 15 轮完整修复。复现时应同时统计模型请求、求解提交、
修复次数与 wall time，不能只对齐配置字段名称。[P1，§2.1][C10]

## 5. 运行完成、后处理完成和物理正确分别是谁判断

### 5.1 固定源码的自动门槛

`run_simulation_local()` 将“解析出的错误列表为空”映射为 completed；图路由还检查 ODB 是否存在，
再进入可视化。当前检查路径没有独立重新验收几何、材料、边界条件、载荷、结果容差的物理 oracle。
主程序图执行结束后的成功文案也不能替代这一验收。[C1][C6][C7]

需要注意以下具体实现事实及其推论：

| 源码事实 | 能作出的有限判断 |
|---|---|
| `check_Abaqus_errors()` 主要扫描 `log*` 和 `.dat` 中的错误；当前 `.dat` 提取器在首段结束后停止 | 不能把它视为完整、多文件的求解状态审计 |
| runner 写出 `AbaqusInput.out/.err`，但上述解析器没有按这两个文件名读取 | 其中的进程或超时信息未必进入错误列表 |
| `communicate(timeout=...)` 确实执行超时控制；超时后调用直接进程的 `kill()` | 不能说完全没有超时；也未看到准确终止 Windows 进程树的机制 |
| 未见退出码到严格运行结果的判定，也未见 ODB 与本次输入的 hash/freshness 绑定 | 仅凭错误为空和 ODB 存在，不能排除漏报或旧产物被使用的可能 |

最后一列是**静态分析风险**，本轮没有构造失败任务进行复现，不能写成已证实发生的运行事故。[C6][C7]

### 5.2 可视化有真实工作，但输出范围有限

固定脚本读取最后一个 step 的最后一帧，输出位移大小及分量云图、节点位移 CSV，并记录开始、完成、
错误标记。节点会等待这些标记，而不是简单启动 Viewer 就立即认定后处理成功。[C9]

同时，这一固定脚本主要围绕 `U` 工作，不能据此声称实现了任意用户输出要求的自动提取，更没有把
位移、应力、反力与独立参考解统一比较。读到有效 ODB、成功导出 CSV，与证明任务正确仍是不同层次。

### 5.3 论文评测另有结果正确性判断

论文 §3.1 明确区分检索准确率、仿真执行成功率和结果准确率。结果主要通过 Abaqus benchmark 与专家审查
判断，部分案例还对照解析解。因此，“开源运行门槛没有独立 oracle”与“论文报告了物理结果检查”
可以同时成立。[P1，§3.1、附录 A]

这也是本项目需要继续保持的边界：普通 CLI 的
[`execution_evidence`](../adr/0019-separate-product-execution-evidence-from-evaluation-oracles.md)
与固定 evaluator 的 `task_oracle` 分开，既不把执行证据夸大为物理验收，也不否认具有明确 oracle 的
固定算例已经验证的范围。

## 6. 论文是怎样测评的

### 6.1 题集来源与主要结果

50 题中，40 题来自检索库案例的参数修改，10 题为库外问题。修改涉及几何、材料、载荷或约束。
测试覆盖静力、非线性材料、动力学、屈曲和复合材料五组。[P1，§3.1]

下表只摘录理解评测所需的结果，数字来自 Table 3（PDF 第 13 页）。

| 题组 | 题数 | 成功数 | 检索准确率 | 执行成功率 | 作者判定的结果准确率 |
|---|---:|---:|---:|---:|---:|
| 库内案例修改 | 40 | 37 | 85%（34/40） | 92.5% | 92.5% |
| 库外问题 | 10 | 6 | 未定义 | 60% | 60% |
| 合计 | 50 | 43 | 未定义 | 86% | 86% |

**分析：**86% 对应这套题集、配置和作者判据下的 43/50，并非所有工程请求的预期成功率。
40 题的设计有利于观察案例迁移，但不是案例家族隔离的陌生问题测试。库外 10 题提供了额外证据，
样本量仍然小；库内外难度和任务分布也不相同。因此，92.5% 与 60% 的差不能单独当作 RAG 的因果增益。

成本部分正文明确描述的是**成功案例条件下**的平均值：库内约 28,761 tokens/157 秒，
库外约 48,200 tokens/312 秒。不能把它们写成包含失败与耗尽重试在内的平均任务成本。[P1，§3.1]
比较成本时还需要统一模型、预算、失败处理和统计口径。

### 6.2 RAG 和 Reviewer 的消融

Table 4 使用 20 题、Opus 4.6、temperature=0，三组结果如下（PDF 第 16 页）。

| RAG | Reviewer | 执行成功率 | 结果准确率 | 论文列出的总 tokens | 总完成时间（秒） |
|---|---|---:|---:|---:|---:|
| 开 | 开 | 90%（18/20） | 90% | 634,690 | 3,518.33 |
| 关 | 开 | 80%（16/20） | 80% | 2,203,778 | 7,757.89 |
| 开 | 关 | 45%（9/20） | 45% | 246,622 | 1,859.41 |

由该表可计算：在 Reviewer 开启时，RAG 对应净增 2 道成功题；在 RAG 开启时，Reviewer 对应净增 9 道。
这些观察支持在该设置下完整参考与运行修复有用，但需要保留三个限定。

第一，没有“RAG 关、Reviewer 关”这一格，不能完整拆出两者交互。第二，关闭 Reviewer 同时改变了
错误后的修复机会，不能据此证明“必须由另一个 Agent 修复”，因为没有同模型、同预算的单 Agent 工具循环
对照。第三，temperature=0 不是重复试验；表中比例没有给出跨重复运行的分布，不能直接解释为稳定概率。

低 token 的无 Reviewer 组也不能简单称为更高效：它成功的任务更少。迁移到本项目时，应同时报告
全部尝试成本、通过任务成本和预算耗尽率，避免通过降低交付率得到表面成本改善。

| RAG | Opus 4.6：执行 / 结果 | GPT-5.2：执行 / 结果 |
|---|---:|---:|

### 6.4 解析验证具体证明了什么

附录 A.1 用四边简支矩形板的线性屈曲作对照。问题为 1 m × 3 m、厚 2 mm 的板，
`E=70,000 N/mm²`、`ν=0.33`，采用 10×30 的 S4R 网格。
解析表达式使用 `D=Eh³/[12(1−ν²)]` 和 `Ncr=4π²D/b²`，给出理论临界力 2.0675 N/mm，
仿真值为 2.1026 N/mm，报告相对误差约 1.70%。[P2，第 24–25 页]

文中的 98.30% accuracy 对应这个标量结果的相对误差补数，不是 50 题成功率，也不是模型的概率置信度。
这一案例证明作者提供了可核查的数值对照；它不把全部复杂非线性案例自动转化为统一、自动化的误差验收。

### 6.5 输入详细程度与可复现性

Figure 3、Figure 6 和附录 C 中，有些请求明确给出单元、边界、网格布局乃至构造线索。
这有助于完成指定模型，但必须与“仅根据开放式工程目标自主选建模假设”区分。[P1，§3.1–3.2、附录 C]

本轮检查的 `AbaqusBench_noArg.py` 是单次任务启动入口：它指定需求文件和输出目录并启动主程序。
未在该入口及检查到的文件中找到与论文 50 题逐项对应的完整 benchmark manifest、统一结果 oracle、
重复运行汇总和置信区间计算链路。因此不能仅凭文件名里的 Bench 宣称开源评测可直接一键复现。[C11]

要做真正复现，需要进一步固定每题原始请求、与案例库的对应关系、参考结果和容差、模型版本、预算、
失败轨迹及聚合脚本。这里列的是复现所需证据，不是本轮已经完成的工作。

## 7. 对本项目的可迁移经验

当前项目路线见[架构总览](../architecture/overview.md)与
[首轮 CodingRun 决定](../adr/0008-pydantic-ai-harness-abaqus-coding-run.md)。下表比较的是职责，
不比较不同题集上的绝对成功率。

| 维度 | AbaqusAgent 固定实现 | 本项目需要对齐的边界 |
|---|---|---|
| 主要生成物 | 直接构造 INP | 普通 CAE Python 建模、INP 求解、独立 ODB 提取三阶段 |
| 领域材料 | 完整案例与生成/修复提示 | Skill、精确 API Catalog、按需官方文档各有职责；案例属于可研究的补充 |
| 编排 | 多角色 LangGraph 节点 | 当前为单一 Pydantic AI Harness Coder；角色拆分不是迁移前提 |
| 缺信息 | 检测、报告并停止本次图执行 | 必需物理输入须澄清，不能用模板数值补造 |
| 运行验收 | 错误解析、ODB 存在、后处理标记 | 受控运行证据和固定任务 oracle 分开 |
| 泛化证据 | 40 个案例修改加 10 个库外问题 | 本项目固定合同的小样本结果也不能外推为通用能力 |

### 7.1 可优先研究的内容

**建模案例作为带条件的参考。** 与其只保存代码，可保留问题定义、建模假设、采用理由、输入来源、
适用条件、预期输出及验证方法。这样才能判断该案例提供的是可迁移方法，还是恰好能运行的一组数值。
这是本笔记建议的案例记录方式，并非声称 AbaqusAgent 已完整实现这些字段。

**显式追踪任务与案例的差异。** 让同一个 Coder 说明需要保留和改变的几何、约束、载荷、材料、分析步及
输出即可研究这条思路，不必先引入另一个规划 Agent。真正需要检验的是最终脚本是否保留用户要求，
而非模型是否输出了一份看似完整的比较表。

**修复时保留证据与语义约束。** 原始运行错误、当前文件和历史尝试有助于避免无依据修改；与此同时，
修复后的产物仍由宿主验收。参考案例、日志建议和模型自评均不拥有改变用户物理任务的权限。

以上三点是候选经验，未在本轮加入产品，也没有新增案例库、分类 Agent 或跨任务记忆。

### 7.2 怎样验证迁移是否值得

一个有解释力的对照应固定骨干模型、原始请求、预算、工具权限和独立 verifier，只改变是否提供完整案例。
测试需要区分同案例参数修改、相近结构迁移和案例家族隔离的新问题；缺少物理输入与参考不适用的任务也
应有明确的澄清/停止期望。这些条件用于区分“会改模板”和“能作新的建模决策”。

检索命中、正确使用证据、物理任务通过和成本应分开统计。检索到了目标案例却误继承载荷，与未命中但
通过可靠推理解决问题，是两种不同结果。只有在这些边界下观察到收益，才值得决定是否增加新知识源或
改变编排；论文中的模块数量和单组成功率本身不构成采用理由。

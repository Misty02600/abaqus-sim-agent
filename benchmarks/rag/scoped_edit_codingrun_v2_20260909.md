# 受保护编辑真实 CodingRun v2：正常编辑通过，知识冲突仍未完全解决

## 结论

三条真实 Go/Flash CodingRun 都只将 `region='LEFT'` 改为
`region=odb.rootAssembly.nodeSets['LEFT']`。应用后的范围与固定 host AST 答案均为 **3/3**；
每条都是 read → edit → read → typed ready，4 次模型请求、3 次文件工具调用，没有被拒绝的越界尝试。

这证明当前保护与本题的正常文件编辑路径兼容，不证明拒绝后修复能力，也不证明模型已经能可靠处理
证据冲突。普通 service 三次完成均只是 `execution_evidence`；代码答案由另行 host-only AST 检查，
没有执行 Abaqus 或读取 ODB。

| 条件 | 应用范围 | 固定代码答案 | 依据和不确定性表达 | 模型请求 / 文件工具 |
|---|---|---|---|---|
| 充分 | 通过 | 正确 | 对本题充分：串联 E1–E4，说明 stub 来源及未运行验证 | 4 / 3 |
| 缺失 | 通过 | 正确 | 部分：承认 not_found 是证据缺口；过程明确依赖已有知识，最终“脚本参考的标准用法”仍没有清楚区分本次取得的依据 | 4 / 3 |
| 合成冲突 | 通过 | 正确 | 部分：承认冲突与未运行验证，但未明确保留两条均为未验证笔记的限定，不能视为可靠消解冲突 | 4 / 3 |

## 解释上还剩什么

缺失组没有把 not_found 当作运行时对象不存在，也没有新增 fallback、helper 或实例遍历；它保留了
用户指定的装配层 LEFT 事实。限制在于：最终摘要仍将来源表述为“Abaqus 2024 ODB 脚本参考的标准用法”，
没有清楚说这是既有知识、不是本次查到的参考。

冲突组在过程里明确诉诸自身 API 记忆，最终承认对象引用未经执行验证。但它把 F1 与“标准 API”并列，
又以 F2 没给出替代接口作为选 F1 的理由；这些并不能独立证明 F1 的来源可靠。F1/F2 同为合成未验证
笔记这一限定没有在最终解释中明确保留。它还扩展声称 region 可以是 `MeshRegion`，本组资料没有支持
这一说法；本报告不把它当作已验证 API 事实。

选出的代码确实正确，因此不能仅因模型选择 F1 就说它无视冲突；也不能反过来把正确答案当成冲突已被
可靠解决。预先冻结的完整来源/不确定性标准仍未满足。三组都没停下，故没有观测到真实“报告缺口且不改
文件”的路径，更没有真正无法消解的冲突样本证据。

## 额外观察：表达式定位成本

缺失组和冲突组在输出中多次手工数绝对字符偏移，出现反复计数错误后才做正确修改。宿主冻结的
`[164,170)` 本来就正确对应 `'LEFT'`，不是合同定位错误。它暴露了接口只呈现偏移时的额外解释负担；
三组最终仍都是 4 次模型请求，不能据此声称已经产生更多请求或确定的时间开销。

本批未据这些输出改提示词或再跑样本。若以后改善目标展示，应由宿主从原始 source/span 导出原表达式
与行列，仍由原区间拥有权限；这是后续候选，不是已实施能力。

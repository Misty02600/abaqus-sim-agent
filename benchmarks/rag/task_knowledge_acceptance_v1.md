# RAG知识需求与验收口径 v1

状态：**定义已整理，尚未按此口径重新评分**。这是对已暴露development任务的验收重整，不是新held-out，不改变已有请求、排名、gold或分数，也不要求本轮修改检索算法。

## 先明确我们在验收什么

五条检索问题实际来自三个用户任务：API离线修正、Riks技术意见、warning记录分析。Riks有两次查询，warning有两次查询，不能将它们视为五个独立任务。

判定基准是**原始用户任务**，不是Agent中途自己提出的每个问题。每个任务分开检查：

1. **答案**：是否回答必需事实，结论是否正确、完整或恰当地带有条件。
2. **依据**：必需事实以及答案主动增加的重要主张，是否由实际送达的资料支持；资料的版本和适用范围是否匹配。
3. **行动边界**：是否遵守只改指定表达式、只写意见、不运行Abaqus、不改物理模型等约束。

正确答案可以缺乏检索依据，证据充分也可能被模型解释错误；这两种情况必须分开记录。不能以“流程10/10”替代答案验收，也不能将过去“指定单元1/3”当成整体RAG成功率。

## 三个任务的知识需求

| 原始任务 | 必须完成的知识工作 | 不应额外强加的要求 |
|---|---|---|
| API离线修正 | 说明本次集合region应传对象而非名字；给出装配层LEFT的正确获取表达式并解释对象关系 | 要求先提供本地ODB、运行Abaqus，或证明所有getSubset重载都只接受OdbSet |
| Riks技术意见 | 解释为什么可能适合给定极限点问题；比例关系和比例因子的含义；为什么不是通用不收敛修复 | 强制回答Agent自行引入的“是否只能使用力型载荷”分支，或强制命中BC单元 |
| warning记录分析 | 说明摘录能/不能证明什么；条件性解释精确输出与增量安排、成本的关系；提出具体后续检查 | 保证作业已收敛或已失败；在procedure未知时直接套用Direct Cyclic规则；取消用户精确输出要求 |

### A. API：集合对象访问，而非一般“节点集知识”

必答事实有两项：

- 针对按集合提取这次调用，区分`'LEFT'`字符串与对应`OdbSet`对象；不要把上下文内的类型要求说成全部重载只有一种合法对象。
- 修正表达式为`field.getSubset(region=odb.rootAssembly.nodeSets['LEFT'])`，说明`rootAssembly`、`nodeSets`仓库和取得对象的关系。

用户已经声明集合位于装配层。只改region表达式，不改变文件、step/frame/field或close逻辑；写`analysis.json`说明依据，不运行Abaqus。可以明确说“静态修正，未检查本地ODB”，不能把没有本地ODB当成任务无法完成的理由。

本次核对了hash绑定的`abqpy-2024.10`包中`FieldOutput.getSubset(region: OdbSet)`、`OdbAssemblyBase.nodeSets`及`OdbBase.rootAssembly`资料。这支持版本化的静态API推理，**不是Abaqus执行证据**。尝试读取2024参考指南网页时得到403，因此未将其内容记为已核验来源。

如果答案自称“已有2024 runtime验证”，必须核对该运行证据确实覆盖本次对象/重载；`OdbMeshNode`调用成功不能自动证明`OdbSet`调用路径已执行。代码可能正确、引用的依据却不充分，要分开判定。

### B. Riks：适用性意见，不是载荷种类穷举

必答事实有三项：

- 用弧长推进静力平衡路径、将载荷大小纳入未知量的基本机制，以及它与用户所给极限点情形的联系。
- 可变载荷模式的比例关系和比例因子由求解确定；若讨论dead load，不应误称其也必然随比例因子变化。
- 至少一个有依据的适用边界及原因，例如时间/速率效应或分岔路径处理；不能保证切换Riks就会修复未知建模错误。

“非零位移能否作为缩放驱动”“是否只能用力型载荷”并非原任务独立要求。**不主动展开时，不应因没命中BC段落而判任务失败；一旦主动断言，就必须审查该断言。** 不能用Loads列表或BC短段落替代对排他规则的直接证明。

历史答案确实主动增加了“确认均为力型载荷后再使用Riks”等前提，这应进入“额外主张的依据审查”，而不是通过强制BC chunk命中来间接评分。本次不据此宣布该历史答案的新分数，也不在证据不足时反向断言所有非零位移方案都受支持。

本地2026 FD02手册的The Riks Method、Proportional Loading、Material Options和Bifurcation章节提供核心概念起点；BC、Predefined Fields、Output及Ending a Riks Analysis Step仅在对应主张被讨论时补充核对。不能据2026资料直接宣称已验证2024所有行为相同。

### C. warning：有条件地解释，不替未知作业下结论

必答事实有四项：

- 一行warning既不足以证明不收敛，也不足以证明成功或无害。
- 在适用的Standard时间域过程中，精确输出时刻可能影响增量安排；不能忽略最小增量限制或procedure例外，承诺所有过程都一定精确命中。
- 可能增加增量数及成本，但不能把这种可能性说成当前已经发生的故障。
- 下一步检查应具体：作业完成/终止与增量记录、收敛/错误消息、step类型以及精确输出设置。

未提供procedure和完整日志时，带前提的解释及检查建议就是合法结果。不能把“本摘录没有其他错误”改成“完整作业没有错误”，也不能擅自运行求解或删除输出要求。

一般机制可由Time Domain Analysis: Time Incrementation及消息文件说明共同支持。Direct Cyclic/低周疲劳的精确输出限制只在相应procedure成立时适用；未知时只能作为明确标注的条件分支。两次warning查询共用同一任务验收，不重复计权。

## 来源与评分原则

机器定义包含**9项必答事实、7类按主张触发的检查**，以及任务行动边界。每个事实记录以下内容，而非只记录chunk ID：

- 答案实际说了什么；未提及的可选分支记`not_triggered`。
- 在答案生成前实际送达的哪些证据支持它；不能事后把评审者能打开的全文算成模型已收到。
- 原文位置、版本、适用条件和推理理由；可以由多段资料共同支持。
- 支持状态：supported、partial、missing、contradicted或scope/version mismatch。

允许任何经核对的等价来源，不要求某个固定URL、页名或单元ID。JSON里的`seed_unit_id`仅帮助定位已知来源；同ID出现不是充分条件，换一种可靠来源也不应判失败。

记录“答案正确性”“依据充分性”“行动合规”三个结果，不把它们揉成一个百分比。缺资料、资料在库但未召回、召回后未送达、送达后误用，应分别归因。错误或缺乏依据的重要主张不能被其他无关正确片段抵消。
